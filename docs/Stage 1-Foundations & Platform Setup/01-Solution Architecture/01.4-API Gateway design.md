# API Gateway Design

The API Gateway is the sole external entry point for the Control Panel Shell, users, and external integrations. Backend services are private and are never directly exposed to browsers or third parties.

## Responsibilities

- Terminate TLS and route `/api/v1/auth`, `/customers`, `/bookings`, `/scheduling`, `/jobs`, `/payments`, and `/notifications`.
- Validate JWT signature, issuer, audience, expiry, and required claims from Auth.
- Apply rate limits, request-size/schema validation, CORS, API versioning, and WAF policies.
- Propagate `correlationId`, trace context, and tenant context; emit access metrics and audit hooks.
- Aggregate read-only responses where useful without owning domain data.
- Translate downstream failures into the canonical envelope; retry only safe/idempotent operations.

The Gateway performs coarse authentication and policy checks. Each target service independently enforces tenant and resource authorization.

## API envelope

```json
{
  "success": false,
  "data": null,
  "errors": [{"code":"BOOKING_NOT_FOUND","message":"Booking was not found.","details":{}}],
  "correlationId":"corr-123"
}
```

`data` is present for successful results, `errors` is an array (empty on success), and every error item has `code`, `message`, and `details` (which may be `{}`).

## Routing and resilience

Use explicit versioned routes and health-aware load balancing. Enforce bounded timeouts, circuit breakers, and exponential backoff. Do not cache tenant-sensitive responses without tenant-scoped keys and authorization-aware invalidation. The Gateway does not publish domain events directly; services publish facts after durable persistence.
