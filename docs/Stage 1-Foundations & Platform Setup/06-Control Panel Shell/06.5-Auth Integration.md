# Control Panel Shell — Auth Integration

## Purpose and boundaries

Auth is the authoritative service for user authentication, short-lived signed
JSON Web Token (JWT) issuance, roles, and permissions. The Control Panel Shell
uses Auth for sign-in, session-related operations, and current-identity
information through the API Gateway's `/api/v1/auth/*` route group.

The Shell is responsible for presenting sign-in and signed-in states and
attaching the caller's authentication and correlation context to Gateway
requests. It does not issue tokens, manage roles or permissions, or make final
authorization decisions. The Gateway validates JWTs before routing, and each
backend service independently enforces tenant and resource authorization for
its own data.

## Sign-in and session flow

```text
User                 Control Panel Shell       API Gateway             Auth
 |                            |                      |                    |
 |-- open Control Panel ----->|                      |                    |
 |                            |-- sign-in request -->|-- /auth/* -------> |
 |                            |                      |                    |
 |                            |<-- identity/session response ------------|
 |                            |                      |                    |
 |-- use protected page ----->|-- request + JWT ---->| validate JWT       |
 |                            |                      |-- route request -->|
 |                            |<-- response + correlation context --------|
 |<-- render permitted view --|                      |                    |
```

1. An unauthenticated user opening a protected page is directed to the Auth
   sign-in flow exposed through the Gateway.
2. The Shell submits credentials or completes the configured identity-provider
   flow only through the documented Auth/Gateway contract. It must not call a
   private Auth service endpoint.
3. Auth authenticates the user and issues a short-lived signed JWT according
   to the identity contract. The Shell establishes the signed-in session using
   the configured session mechanism and obtains current-identity information
   through `/auth/*`.
4. For protected data requests, the Shell sends the JWT and correlation
   context to the Gateway. The Gateway validates the token before routing the
   request.
5. The Shell renders the response and any authorization-aware presentation
   state. The target service remains responsible for its resource-level access
   decision.

The exact sign-in, refresh, current-identity, and sign-out endpoint names and
payloads are defined by the Auth/Gateway contract. Do not infer new endpoint
paths from this document.

## Session and token handling

- Keep the JWT short-lived and use it only for requests to the API Gateway.
- Never place access tokens, refresh tokens, credentials, or secret values in
  URLs, page markup, browser logs, analytics events, or client-side persistent
  storage such as `localStorage`.
- Select and document one token-custody pattern for the Shell implementation.
  For a server-side session, keep tokens on the server and give the browser
  only a session cookie configured with `Secure`, `HttpOnly`, and an
  appropriate `SameSite` policy. If the chosen architecture requires the
  browser to call the Gateway directly, keep token exposure and lifetime to a
  minimum and follow the approved browser OAuth/OIDC flow.
- Protect state-changing requests against cross-site request forgery when the
  session mechanism uses cookies.
- Do not log JWTs or credentials. Redact authentication material in error
  reporting and telemetry.
- Do not treat decoded JWT claims or Shell-held role/permission state as
  proof of authorization. The Gateway validates the signed token and the
  backend service evaluates the requested resource.

## Identity and tenant context

The current-identity response may provide the signed-in user's identity and
tenant context as defined by the Auth/Gateway contract. The Shell uses that
data to display account and tenant context and to shape the visible experience.
Roles or permissions may inform whether navigation is shown, but that
presentation behavior is not an access-control boundary.

When a user changes tenant context, the Shell must use the supported Auth or
Gateway operation and refresh tenant-sensitive views. It must not trust a
tenant identifier supplied only by the browser, reuse data from the prior
tenant, or assume that a valid JWT grants access to every tenant. The Gateway
and target service validate the trusted tenant context and resource access for
each request.

## Expiry, renewal, and sign-out

- Treat an expired, invalid, or revoked token as unauthenticated; do not retry
  indefinitely with the same token.
- If the Auth contract supports renewal, use only its documented renewal flow
  and handle renewal failure by clearing the local signed-in state and
  returning the user to sign-in.
- On sign-out, invoke the documented Auth/Gateway sign-out operation when
  available, clear the Shell's session state, and remove any locally retained
  authentication material.
- After sign-out, browser back navigation must not expose protected content
  from cached application state. Protected API requests must still be rejected
  if the user revisits a prior URL.
- Do not invent refresh-token behavior or assume that a refresh token is
  issued; follow the Auth contract.

## Error and recovery behavior

The Shell distinguishes authentication failures from authorization denials and
ordinary service errors:

- **Unauthenticated**: prompt the user to sign in again and preserve only a
  safe return path to the requested Shell page.
- **Forbidden**: show an access-denied state without repeatedly redirecting
  to sign-in. A valid identity does not guarantee permission for a particular
  operation.
- **Unavailable Auth/Gateway**: show a recoverable error and retry only
  according to bounded retry guidance. Do not interpret a timeout or service
  failure as successful authentication.
- **Malformed or unexpected response**: fail closed for protected content,
  report a safe diagnostic with the `correlationId` when available, and avoid
  exposing tokens or internal implementation details.

The Gateway response envelope includes `success`, `data`, `errors`, and
`correlationId`. Use the correlation ID when presenting a support reference
or recording a diagnostic, but do not expose sensitive response data.

## Audit and operational requirements

Authentication failures, authorization denials, and administrative identity
changes are audited by the responsible backend components. Shell telemetry
may record the outcome, route, and `correlationId` needed to diagnose a user
flow, but it must not duplicate credentials, token contents, or sensitive
identity data into client-visible logs. Auth and Gateway operations should
provide enough correlation context to trace a request across services.

## Contract dependencies

Before implementation, the Auth/Gateway contract must specify:

- The supported sign-in and sign-out flows and their endpoint paths.
- The current-identity operation and the fields safe for Shell presentation.
- JWT issuer, audience, expiry, required claims, and signing-key validation
  expectations for the Gateway.
- Whether renewal is supported, its mechanism, and failure behavior.
- How tenant context is selected, represented, and refreshed.
- The Shell's token-custody/session pattern and the required cookie and CSRF
  protections, if applicable.
- Authentication and authorization error codes and response behavior.
