# Control Panel Shell Navigation

## Purpose

Navigation helps users move between the Control Panel's operational areas while
keeping the active tenant context and location visible. It is part of the
presentation-only Shell: it organizes pages and reflects the access context
returned by the application, but it does not grant access to data or resources.

The Shell calls the API Gateway only. The Gateway and each backend service
authenticate and authorize requests; hiding or showing a navigation item is
never a security boundary.

## Information architecture

Use a consistent primary navigation for the product's main work areas:

| Destination | Purpose |
| --- | --- |
| Customers | Find and manage customer records. |
| Bookings | Review and manage booking requests and their status. |
| Scheduling | View availability and assignments. |
| Jobs | Follow job execution and completion. |
| Payments | View payment status, refunds, and reconciliation information. |
| Notifications | Review notification preferences, templates, and delivery status. |
| Administration | Reach identity and other administrative views exposed by the Gateway. |

The navigation label describes a user task or domain, not an API implementation
or database table. Keep related pages grouped beneath their domain destination
when additional workflows are introduced. Add a destination only when the
corresponding user-facing view and Gateway contract exist.

The table describes the product's information architecture; the exact page
inventory may evolve as Gateway capabilities are defined. The current Shell
contract documents the base route groups at `/api/v1/auth`, `/customers`,
`/bookings`, `/scheduling`, `/jobs`, `/payments`, and `/notifications`.

## Navigation model

- **Primary navigation** provides persistent access to the top-level areas.
- **Secondary navigation**, where needed, groups related pages within the
  selected area.
- **Breadcrumbs** show the current page's parent hierarchy and provide links
  back to navigable parent pages.
- **Page actions** belong in the page header, not in the navigation, unless an
  action is itself a stable destination.

Keep the navigation hierarchy shallow and labels concise. Use the same label
for a destination wherever it appears, including breadcrumbs and page titles.
Indicate the current page and its parent area so users can understand both
their immediate location and the broader section.

## Visibility and tenant context

The Shell may adapt navigation to the signed-in user's available views and the
active tenant context, using information made available through the documented
Gateway contract. It must not query tenant, module, role, or permission tables
directly, and it must not infer authorization from client-side state alone.

If a destination is unavailable, the Shell may omit it or present it as
unavailable according to the product's UX policy. In either case:

- A hidden or disabled item does not replace request authorization.
- Direct links and manually entered URLs must receive the same backend
  authorization checks as navigation clicks.
- A tenant switch changes the selected display context, but does not grant
  access to that tenant's resources.
- If an API denies access or the tenant context changes, show a safe,
  understandable state and do not render stale tenant-sensitive data.

## Interaction and route behavior

- Selecting a destination updates the active navigation state, page title,
  breadcrumbs, and main content together.
- Each stable page should have a linkable application route so users can open
  or bookmark it directly.
- Back and forward navigation should restore the expected page and visible
  navigation state without bypassing API authorization.
- Preserve the shared Shell frame during navigation. Do not navigate the
  browser directly to private service endpoints.
- When a page depends on asynchronous API work, show the status returned by the
  Gateway and refresh it through Gateway-mediated requests.
- If a route is unknown or unavailable, show an appropriate not-found or
  unavailable view within the Shell rather than exposing implementation
  details.

## Responsive behavior

On wide viewports, keep primary navigation persistently available beside the
main content. On narrow viewports, present it as a toggleable drawer or
equivalent compact control. The compact navigation must:

- Have a clear accessible name and an announced expanded/collapsed state.
- Open and close using keyboard as well as pointer input.
- Move focus into the navigation when opened and return focus to its trigger
  when dismissed.
- Close after a destination is selected where appropriate, without losing the
  newly selected page's focus context.

## Accessibility

- Implement primary and secondary navigation as semantic navigation
  landmarks, with distinct accessible labels when a page has more than one.
- Use links for navigation and buttons for actions such as expanding a
  navigation group.
- Expose the current location programmatically, for example with
  `aria-current="page"` on the active page link.
- Ensure all items are keyboard reachable, focus is visible, and focus order
  follows the visual hierarchy.
- Do not use color or icons as the only indication of a selected, disabled, or
  expanded item; pair icons with text labels.
- Support zoom and narrow viewports without obscuring the current destination
  or requiring horizontal scrolling for the navigation.

## Security and data boundaries

Navigation is a user-interface affordance, not an authorization engine. The
Shell sends the caller's short-lived JWT and correlation context to the API
Gateway. It does not call private services, read PostgreSQL or Key Vault, or
subscribe to domain events. Authorization denials and unavailable resources
must be handled using safe user-facing states; tokens, secret values, internal
event payloads, and sensitive resource details must not be placed in navigation
URLs or labels.
