## Layout structure

The Shell provides a stable application frame around each page. The frame stays
consistent while the page title, actions, content, and status change with the
selected destination.

```text
┌─────────────────────────────────────────────────────────────┐
│ Header: product identity · tenant context · account actions  │
├───────────────┬─────────────────────────────────────────────┤
│ Primary       │ Breadcrumbs                                  │
│ navigation    │ Page title                         Actions  │
│               ├─────────────────────────────────────────────┤
│               │ Page content                                 │
│               │                                              │
└───────────────┴─────────────────────────────────────────────┘
```

### Header

The header identifies the Control Panel and displays the active tenant context
and signed-in account actions. If tenant switching is available to the user,
the selector changes the active display context and refreshes the relevant
views. It does not grant access to tenant data.

### Primary navigation

The primary navigation provides destinations for the product's operational
areas: customers, bookings, scheduling, jobs, payments, notifications, and
administration. The Shell may hide or disable destinations that are unavailable
to the current user, but this is a presentation decision only. The Gateway and
backend services remain responsible for authentication and authorization.

On wide screens, primary navigation occupies a persistent side rail. On narrow
screens, it collapses into a toggleable navigation drawer so page content
remains usable without horizontal scrolling.

### Page header and content

Each destination renders inside the shared content area and uses a consistent
page hierarchy:

1. Breadcrumbs show the current location within the application.
2. The page title names the current task or resource.
3. Optional page actions appear alongside the title when relevant.
4. The main content region displays the selected module's view.

Module views provide page-specific content; the Shell supplies the surrounding
frame and shared navigation. A page must not expose service tables or internal
event payloads as a substitute for a user-facing view.

## Shared presentation behavior

- Keep the active tenant context visible while navigating between areas.
- Preserve the frame when navigating; update the selected destination,
  breadcrumbs, page title, and content.
- Use consistent loading, empty, error, and unavailable states in the content
  region. Display API errors returned through the Gateway without exposing
  internal details or secret values.
- For operations that complete asynchronously, show the status returned by the
  API and refresh it through Gateway-mediated status requests.
- Keep forms and view state local to the presentation layer. Persist business
  data only through the documented Gateway API contract.

## Responsive and accessible layout

- Use semantic landmarks for the header, navigation, and main content.
- Make navigation, tenant controls, forms, and page actions operable by
  keyboard and provide visible focus indicators.
- Give controls accessible names and associate validation feedback with the
  relevant form fields.
- Do not rely on color alone to indicate selection, status, or errors.
- Ensure the navigation drawer can be opened and dismissed with keyboard and
  assistive technology, and return focus to its trigger when dismissed.
- Reflow content for narrow viewports; avoid requiring horizontal scrolling for
  primary tasks.

## Responsibility boundaries

The Shell is presentation-only. It calls the API Gateway, which is the sole
external entry point, and renders the responses it receives. It does not
connect to PostgreSQL, access service-owned tables, call private services
directly, read Key Vault, or subscribe to domain events.

The Shell may present authorization-aware navigation and tenant context, but it
does not enforce tenant or resource access. The Gateway validates caller
identity, and each backend service enforces authorization for its own
resources. The browser must never receive integration secret values.
