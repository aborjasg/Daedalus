# Interaction-Level System Design

## Request interaction

1. The Shell sends an HTTPS request to the API Gateway with a JWT and correlation header.
2. The Gateway validates the JWT, establishes `tenantId`, applies coarse policy, and routes to a private service.
3. The service validates the request, enforces tenant/resource authorization, and reads/writes only its own PostgreSQL schema.
4. The service commits the state change and publishes an event through Azure Service Bus using the event envelope.
5. The Gateway returns the canonical `{success,data,errors,correlationId}` response to the Shell.

## Booking-to-job interaction

Bookings persists `BookingCreated`. Scheduling consumes it, checks availability, and publishes an assignment fact. Jobs consumes the assignment and creates the operational job. Notifications consumes booking/assignment events for customer and staff messages. The Shell observes each state through Gateway APIs; it never reads tables or subscribes to events directly.

## Job-to-payment interaction

Jobs publishes `JobCompleted`. Payments consumes it idempotently and creates or updates a payment intent. Payment provider credentials are resolved from Key Vault references. Payments publishes `PaymentSucceeded` or `PaymentFailed`; Notifications consumes the result. Each step carries the original `correlationId` and `tenantId`.

## Failure handling

Use bounded retries for transient failures, idempotency keys for commands, outbox/inbox records for reliable event delivery, and Service Bus dead-letter queues for poison messages. Return error items with `code`, `message`, and `details`; never leak tokens, secret values, SQL, or cross-tenant existence information.
