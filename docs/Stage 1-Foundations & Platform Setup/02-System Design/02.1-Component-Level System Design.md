# Component-Level System Design

## Runtime components

- **Control Panel Shell:** presentation-only web UI. It owns navigation, layout, local view state, and form validation. It calls the API Gateway and has no domain persistence, service credentials, or direct Service Bus access.
- **API Gateway:** sole public entry point; validates JWTs, routes requests, applies traffic policy, and standardizes envelopes.
- **Auth:** authentication, JWT issuance, users, roles, permissions, and tenant membership.
- **Customers:** customer profile and contact lifecycle.
- **Bookings:** booking request and lifecycle.
- **Scheduling:** availability, assignment, and calendar commitments.
- **Jobs:** operational execution and completion evidence.
- **Payments:** payment intents, provider references, transactions, refunds, and reconciliation.
- **Notifications:** templates, channel delivery, and delivery status.

## Shared platform components

PostgreSQL Flexible Server hosts service-owned schemas. It is one relational platform initially, not a shared domain schema: each service can access only its own schema through its own database identity. Azure Service Bus provides queues/topics for commands and events. Azure Key Vault stores integration secret values; PostgreSQL stores references. Azure Monitor/Application Insights provides logs, metrics, traces, and alerts.

## Component rules

Every service is stateless where practical, validates tenant context, applies resource authorization, emits structured telemetry, and exposes health/readiness endpoints. Domain writes use transactions and an outbox pattern where event publication must be reliable. Consumers are idempotent and use dead-letter queues. Shared libraries may provide transport, telemetry, and envelope primitives, but must not contain shared mutable domain models or bypass ownership boundaries.
