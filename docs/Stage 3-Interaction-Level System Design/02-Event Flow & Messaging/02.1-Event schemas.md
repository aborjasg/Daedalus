# Event Schemas

## Purpose and status

Azure Service Bus is the default asynchronous messaging technology. Use
queues for commands and work distribution, and topics/subscriptions for
domain events. This document records the common event envelope and the
documented event flows. It does not define complete event-specific payload
schemas, queue/topic names, or consumer subscription configuration.

Event contracts are versioned and backward compatible. The current docs do
not specify how a version is represented in the envelope or event type, nor
the exact payload fields for the named events. Each producing service must
define those contracts before publishing them; consumers must not infer
payload fields from database columns or another service's internal model.

## Common event envelope

Every event uses the following documented envelope:

```json
{
  "eventId": "evt-123",
  "eventType": "BookingCreated",
  "occurredAt": "2026-09-18T20:00:00Z",
  "correlationId": "corr-123",
  "tenantId": "tenant-1",
  "sourceService": "Bookings",
  "payload": {}
}
```

The empty `payload` in this example illustrates the envelope only; it is not
a complete or valid `BookingCreated` payload contract.

| Field | Meaning | Contract status |
|---|---|---|
| `eventId` | Identifier used to recognize a delivered event and support idempotent processing. | Field is established; format, scope, and retention are not specified. |
| `eventType` | Stable name for the domain event, such as `BookingCreated`. | Field and some names are established; naming/version policy must be finalized by producers. |
| `occurredAt` | Time the event occurred, represented as a timestamp string in the example. | Field is established; required precision and timestamp validation rules are not specified. |
| `correlationId` | Correlates the event with the operation and related service activity. | Field is established; propagate the originating correlation context. |
| `tenantId` | Tenant scope for the event. | Field is established for tenant-scoped flows; use trusted backend context, not unchecked client data. |
| `sourceService` | Service that produced the event. | Field is established; value is the producer's documented service identity. |
| `payload` | Event-specific domain facts needed by consumers. | Field is established; its schema is owned by the producing service and remains to be defined for each event. |

`tenantId` is the API/event spelling; tenant-scoped PostgreSQL records use
`tenant_id`. A tenant identifier in a message does not itself authorize a
consumer to act on another service's data. Consumers validate the event and
tenant context and enforce authorization for their own operations.

## Documented event flows

The following names and broad responsibilities appear in the current
architecture. This is an inventory of documented flows, not a complete event
catalog or payload definition.

| Event or fact | Producer | Consumer/use | Payload status |
|---|---|---|---|
| `BookingCreated` | Bookings, after durable booking persistence | Scheduling checks tenant-scoped availability; Notifications may consume booking facts for messages. | Exact required fields, types, and event version are not defined. |
| Scheduling assignment/availability result | Scheduling, after persisting its result | Jobs creates an operational job; Notifications may communicate assignment information. | Canonical event name and payload are not defined. |
| `JobCompleted` | Jobs, after authorized completion is committed | Payments consumes it idempotently to create or update a payment intent; Notifications may communicate completion. | Exact required fields, types, and event version are not defined. |
| `PaymentSucceeded` | Payments, after establishing the payment outcome | Notifications consumes the outcome; other consumers require an explicit contract. | Exact required fields, types, and event version are not defined. |
| `PaymentFailed` | Payments, after establishing the payment outcome | Notifications delivers an alert; the Shell reads current status through Gateway APIs. | Exact required fields, types, and event version are not defined. |
| Refund outcome event(s) | Payments | Consumers are not specified in current docs. | Event names and payloads are not defined. |

The event's producer remains the authority for its domain record. Consumers
may maintain a local, non-authoritative projection when required, but must
not read or write the producer's tables. The Gateway does not publish domain
events on behalf of services.

## Payload contract requirements

For every event type and version, the producer's contract must specify:

- The event name and versioning/compatibility policy.
- Every payload field's meaning, type, required/optional/null behavior,
  format, constraints, and enum values.
- The identifiers and tenant scope necessary for consumers to perform their
  documented work without requiring direct database access.
- Whether fields are snapshots of facts at event time or references that a
  consumer must resolve through a documented API.
- Safe handling of personal, financial, or otherwise sensitive data, and
  fields that must never be published (including credentials, tokens, and
  secret values).
- Producer ownership, allowed consumers, ordering/session assumptions, and
  behavior when a consumer needs information not included in the event.

Events should carry only the minimum data needed by their consumers. Do not
copy whole database rows, API response envelopes, or provider payloads into
events by default. HTTP request/response schemas and event schemas are
separate contracts.

## Versioning and compatibility

Event contracts are versioned and backward compatible. The version
representation, compatibility window, and handling of breaking changes are
not specified by current docs and must be agreed by producers and consumers.
Do not silently change the meaning or type of an existing field, remove a
field still required by supported consumers, or reuse an event name for a
different fact.

The common envelope example does not contain an explicit version field.
Before implementation, document whether the version is carried in message
metadata, the event type, or an agreed envelope field; do not assume one
representation from this page. Consumers should reject or quarantine
unsupported versions according to the messaging contract rather than
misinterpret them as a known schema.

## Delivery, processing, and reliability

- Azure Service Bus delivery is at least once. Consumers are idempotent and
  deduplicate using the documented event identity and processing scope.
- A consumer acknowledges a message only after its required processing is
  durable. Persisted consumer effects and duplicate-detection state must be
  coordinated so redelivery does not duplicate business actions.
- Producers publish domain events only after durable state persistence. Use
  the documented outbox/inbox reliability pattern where applicable; exact
  storage and implementation are service-owned.
- Transient failures use bounded retries with backoff. Poison messages are
  dead-lettered and alerted. Define replay and operator recovery so replaying
  a message does not bypass validation, tenant scoping, or idempotency.
- Ordering is guaranteed only within the chosen Service Bus session or
  partition strategy. A consumer must not assume global ordering unless its
  contract explicitly establishes it.
- Commands and work-distribution messages use queues; domain events use
  topics/subscriptions, as selected by the messaging design. Queue/topic
  names, subscriptions, filters, session keys, and retention are not defined
  here.
- Preserve `correlationId` across the initiating operation, event
  publication, consumer processing, logs, metrics, and traces. Correlation
  is for observability, not authorization or deduplication unless a contract
  explicitly says otherwise.

## Security and tenant isolation

- Authenticate service-to-service messaging with the documented Entra
  authentication and per-queue/topic authorization. Use TLS and least
  privilege.
- Treat messages as untrusted input at the consumer boundary: validate
  envelope and payload schema, producer identity, tenant scope, and domain
  preconditions before acting.
- Use `tenantId` in event contracts and `tenant_id` in PostgreSQL. A consumer
  scopes database operations to the validated tenant context; missing,
  malformed, or mismatched context must not broaden access.
- Never publish credentials, access tokens, secret values, Key Vault secret
  contents, or unnecessary sensitive provider data. PostgreSQL may hold a
  Key Vault reference where applicable, but possession of that reference
  does not authorize secret access.
- Logs, dead-letter diagnostics, and traces must redact sensitive payload
  fields. Error and operator views must not disclose another tenant's
  resource existence.

## Event example template

Use this as a documentation template only. Replace the payload placeholder
with the producing service's approved, versioned schema before publishing an
event:

```json
{
  "eventId": "<unique event identifier>",
  "eventType": "<documented event name>",
  "occurredAt": "<documented timestamp format>",
  "correlationId": "<originating correlation identifier>",
  "tenantId": "<trusted tenant identifier when tenant-scoped>",
  "sourceService": "<producing service>",
  "payload": {
    "fieldsDefinedByTheProducingService": "..."
  }
}
```

The placeholder is not a literal payload contract. Define whether `tenantId`
is required for each event; do not omit tenant scope from tenant-owned work
or invent tenant scope for explicitly global events.

## Contract checklist

Before publishing an event, its owner and consumers must agree on:

- Event name, version representation, schema, and backward-compatibility
  policy.
- Producer, authorized consumers, and business meaning of each field.
- Tenant context, producer authentication, and consumer authorization.
- Queue/topic, subscription/filter, delivery, ordering, retry, dead-letter,
  and replay behavior.
- Idempotency/deduplication scope and durable-processing/acknowledgement
  rules.
- Outbox/inbox requirements, correlation propagation, and operational
  observability.
- Data minimization, retention, redaction, and exclusion of secrets.

Until an event-specific contract is approved, treat the names and flows in
the inventory as architectural references only; do not infer a production
payload from service tables, example envelopes, or this checklist.
