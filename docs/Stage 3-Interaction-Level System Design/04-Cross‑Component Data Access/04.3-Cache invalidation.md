# Cross-Component Cache Invalidation

## Purpose and status

Caches may reduce repeated reads of data obtained through an allowed service
API, consumer-owned event projection, or approved read-only Gateway
aggregation. A cache is a non-authoritative copy: the service that owns the
domain remains the source of truth and the authority for access to its
records.

The current `/docs` define isolation and invalidation requirements, but do
not select a cache technology, define a platform-wide invalidation protocol,
specify cache lifetimes, or establish cache-specific event types. This
document sets design constraints; each cache's owner must document its
policy before implementation. Do not infer Redis, a particular TTL, or a
generic invalidation event.

## Ownership and scope

- The component that creates and serves a cache owns its keys, stored
  representation, expiry, invalidation, recovery, and observability.
- Caching does not transfer data ownership or permit direct access to
  another service's schema. Populate caches from an allowed read path:
  documented APIs, documented versioned events, or another approved
  projection.
- A consumer-owned event projection is persistent application state, not
  merely an evictable performance cache. Its owner must separately define
  event processing, replay, reconciliation, and projection recovery.
- The Gateway may cache an approved read-only aggregate only under that
  aggregate's documented freshness and authorization policy. It must not
  query service tables to populate or refresh a cache.
- The Shell may retain transient, non-authoritative view data, but it does
  not own server-side domain caches or determine authorization from cached
  state.

## Invalidation and refresh triggers

For each cached value, identify which changes can make it stale and define
how the cache reacts. Depending on the data and its approved contracts, the
owner may:

1. **Invalidate on an owner notification:** consume a documented event
   describing a relevant committed change, then evict or refresh the
   affected cache entry. Events are delivered at least once; handling must
   be idempotent and tolerate duplicates and out-of-order arrival.
2. **Expire after a documented freshness window:** use a defined TTL when
   delayed visibility is acceptable. Expiry is a bound on cache residence,
   not proof that the value is current until it expires.
3. **Refresh on demand:** obtain current data from the owning API when an
   entry is missing, expired, invalidated, or too stale for the operation.
   Define whether stale data may be served while refresh is attempted; do
   not use stale data for authorization or other decisions requiring
   authoritative state.
4. **Invalidate explicitly after a successful owner-mediated command:**
   evict or refresh related entries after the owning service confirms the
   write. A timeout or lost response is ambiguous; reconcile through the
   owner's API rather than assuming either success or failure.
5. **Clear on identity or tenant context change:** remove or make
   inaccessible client-side and server-side entries scoped to the prior
   identity, membership, permissions, or tenant. A cache hit must never
   bypass a fresh authorization check.

Only rely on an event-driven strategy when the relevant event and its
meaning are documented by the producer. Do not invent event names, payload
fields, ordering guarantees, or delivery semantics beyond the established
event contract. If a change can occur without a notification, define a
fallback such as bounded TTL, refresh-on-read, or owner-API reconciliation.

## Tenant and authorization isolation

- Include tenant scope in every cache key for tenant-owned data. Include
  additional authorization-relevant scope when the cached response varies
  by principal, role, permission set, resource access, or other policy
  context.
- Construct scope from validated identity and trusted server-side context,
  not from an untrusted request parameter alone. API/event contracts use
  `tenantId`; persisted PostgreSQL records use `tenant_id`.
- Re-authorize protected reads with the owning service on cache misses and
  on every cache hit as required by the owning service's contract. Possession
  of a cache key or a previous successful read is not authorization.
- Invalidate or make entries unreachable when identity, tenant membership,
  roles, permissions, resource access, or relevant policy changes. Define
  how revocation takes effect; do not serve a protected response based only
  on an old authorization result.
- Do not share entries across tenants or authorization contexts, including
  through unscoped fallback keys, shared client state, or an aggregate
  response assembled from differently authorized sources.
- Never cache secret values, access tokens, credentials, or sensitive
  provider material in general-purpose application or response caches.

## Consistency, races, and failure behavior

Cache behavior must match the consumer's freshness requirement. Reads that
make authoritative decisions, enforce access, accept a quote for a booking,
or otherwise require current source state must consult the owning service
through its documented contract; a cache or event projection alone is not
sufficient.

The cache owner must consider these cases in its policy:

- An invalidation arrives before or after a concurrent cache fill.
- Duplicate or delayed events attempt to invalidate or refresh an entry
  after a newer value has been written.
- A source write commits but notification delivery or cache invalidation
  fails.
- A refresh fails, times out, or returns an authorization denial.
- A stale entry is present after a user, permission, or tenant change.

Use versioning, compare-before-write, eviction, or another documented
mechanism where needed to prevent older data from replacing newer data.
Define recovery and reconciliation for missed notifications or cache
outages. Do not silently convert a cache miss, stale result, refresh error,
or authorization denial into a success-shaped default. Follow the
request/response contract and expose only safe failure information with
`correlationId`.

## Cache policy checklist

Before enabling a cache, document:

1. The cache owner, data source, source of truth, and fields being cached.
2. The exact key scope, including tenant and any authorization context.
3. The freshness requirement, TTL or refresh policy, and whether stale data
   may ever be served.
4. Invalidation triggers and their documented APIs/events, including
   duplicate/out-of-order handling and fallback if invalidation is missed.
5. Behavior on identity, tenant, permission, or resource-access changes.
6. Cache-fill races, source failures, revocation, recovery, and
   reconciliation behavior.
7. Metrics and safe diagnostics for hits, misses, stale responses,
   invalidations, refresh failures, and cache availability.

Cache duration, policy, and invalidation events are not globally prescribed
by current documentation. Set them for each approved use case; do not
introduce caching where the required isolation, authorization, or freshness
guarantees cannot be maintained.
