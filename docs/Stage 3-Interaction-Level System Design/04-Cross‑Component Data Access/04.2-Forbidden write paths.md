# Forbidden Cross-Component Write Paths

## Purpose and governing rule

Each service is the sole writer and authority for its own domain records and
PostgreSQL schema. A service may change another domain only through an
explicit, documented command contract handled by the service that owns that
domain. Hosting multiple schemas on one PostgreSQL server does not grant
services permission to modify one another's data.

This document defines prohibited write patterns and ownership constraints.
It does not create new API endpoints, event types, workflows, or ownership
assignments. Define those with the affected service owners before
implementation. See [04.1-Allowed read paths.md](./04.1-Allowed%20read%20paths.md)
for approved cross-component read patterns.

## Forbidden write paths

- **Direct cross-schema writes:** A service, Gateway, Shell, worker, or
  integration must not insert, update, delete, or run migrations against
  another service's tables, including through cross-schema SQL, foreign
  keys, stored procedures, triggers, views, or database functions.
- **Shared database credentials:** Do not give a service a database identity
  that can write outside its owned schema. Do not use a privileged shared
  credential from application code, background jobs, scripts, or local
  tooling to bypass service ownership.
- **Gateway or Shell persistence:** The API Gateway routes and may perform
  documented read-only aggregation, but it does not write domain records on
  behalf of services. The Control Panel Shell calls the Gateway and does
  not connect to PostgreSQL or private service endpoints.
- **Cross-service transactions:** Do not wrap writes to multiple services'
  schemas in one database transaction or rely on a global transaction,
  shared ORM model, or cross-schema join to keep domains consistent.
- **Writes disguised as reads:** A read endpoint, cache refresh, projection
  query, report, or aggregate must not mutate source-owned records as a
  side effect. Any command or state transition must use an explicitly
  documented write contract.
- **Event consumers changing producer data:** A consumer may persist its
  own effect in its own schema after validating a documented event. It must
  not update or repair the producer's records directly, and it must not
  treat an event fact as permission to write into the producer's domain.
- **Client-selected ownership:** Do not accept client-supplied tenant,
  owner, or service identifiers as authority to select which records or
  schema to modify. The owning service establishes trusted context and
  authorizes the operation.
- **Out-of-band edits:** Do not use manual SQL, admin scripts, database
  consoles, or deployment/migration jobs to change another service's live
  domain data outside its documented operational and migration ownership.
  Correct data through the owning service's approved operation or a
  documented owner-controlled recovery procedure.

## Permitted cross-service state changes

Cross-service work is allowed only when it preserves ownership:

1. A caller submits a command through the public Gateway or an explicitly
   documented private service API/command contract.
2. The target owner authenticates the caller, validates the command and
   trusted tenant context, applies resource authorization, and writes only
   its own records.
3. If other services must react, the owner publishes a documented,
   versioned event after its state is durably committed. Consumers validate
   the event and write only their own effects.
4. Each service handles its own retries, idempotency, and recovery. A
   multi-service workflow coordinates outcomes through documented
   contracts; it does not bypass ownership to force atomicity.

An event notification is not automatically a command. Consumers must act
only on documented event semantics and may not reinterpret a fact event as
an instruction to alter another service's state.

## Ownership examples

- **Quote to booking:** Quote Estimator owns quote calculations and quote
  results. Bookings owns booking lifecycle and the accepted booking-price
  snapshot. Bookings may validate or revalidate a quote through an
  agreed owner-controlled API or event contract; it must not read or modify
  the Quote Estimator schema directly. The Shell cannot submit an
  authoritative price snapshot of its own.
- **Booking and scheduling:** Bookings publishes a documented booking fact
  after its own commit. Scheduling consumes it and writes any assignment
  only to Scheduling-owned persistence. Scheduling does not mutate Bookings
  records to mark an assignment.
- **Job completion and payment:** Jobs owns completion evidence and status.
  Payments consumes a documented completion fact and writes payment
  intents, transactions, and reconciliation state in its own domain.
  Payments does not edit a Job to indicate payment outcome.
- **Integration credentials:** The service owning the provider integration
  manages its connection and metadata; secret values belong in Key Vault.
  Another service must not write its integration records or secret
  references directly.

These examples follow the documented ownership boundaries; they do not
define missing endpoint paths, event payloads, or exact state transitions.

## Consistency, security, and recovery

- Resolve tenant context from validated identity and authenticated
  service-to-service context, not an untrusted request body or event alone.
  API/event contracts use `tenantId`; tenant-scoped PostgreSQL records use
  `tenant_id`.
- The target service independently authorizes each write to its resources.
  A valid JWT, access to another service, or a message on Service Bus does
  not grant permission to mutate the target domain.
- Use service-owned transactions for local writes. When publication must
  follow a durable state change, use the documented outbox/inbox approach;
  consumers acknowledge only after their own required effects and
  deduplication state are durable.
- Make retried commands safe according to their documented idempotency
  contract. Do not retry non-idempotent writes without an agreed mechanism.
- Propagate `correlationId` and record safe telemetry. Never log or publish
  tokens, credentials, Key Vault secret values, or unnecessary sensitive
  records.
- On validation, authorization, dependency, or partial workflow failure,
  report the outcome through the documented contract. Do not silently
  compensate by directly changing another service's database.

## Review checklist

Before approving a cross-component write, document:

1. The source caller, target owning service, purpose, and command semantics.
2. The versioned API or command/event contract, including validation and
   error behavior.
3. Trusted tenant context, authentication, resource authorization, and
   least-privilege service identity.
4. The owner-local records changed, transaction boundary, idempotency, and
   audit requirements.
5. Any downstream events, consumer-owned effects, consistency expectations,
   retries, and recovery/compensation procedure.
6. Confirmation that no participant requires direct writes to another
   service's schema or an implicit distributed transaction.
