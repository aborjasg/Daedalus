# Allowed Cross-Component Read Paths

## Purpose and governing rule

Each service is authoritative for its own domain records and PostgreSQL
schema. A component that needs another service's data must use a documented
read path owned by that service; sharing a PostgreSQL server does not grant
permission to query another schema. Cross-component reads must preserve
tenant isolation, resource authorization, source ownership, and the freshness
semantics of the chosen path.

This document defines permitted patterns, not new endpoint, event, or
aggregation contracts. The owning service and affected consumers must
document those contracts before implementation.

## Allowed paths

| Read path | Appropriate use | Authority and constraints |
|---|---|---|
| **Owner-local database read** | A service reads or updates records in its own schema to fulfill its operations. | The service is authoritative for those records and enforces tenant and resource authorization. It must not query another service's schema. |
| **Documented service API** | A caller needs current data or a decision owned by another service, especially for an immediate user-facing result or validation. | The source service remains authoritative and authorizes the request. Use the documented private service-to-service API and authenticated service identity for east-west calls, or the public Gateway route for Shell/external clients. Do not invent endpoints or bypass the Gateway from the Shell. |
| **Consumer-owned event projection** | A service repeatedly needs a bounded set of facts from another domain and can tolerate asynchronous updates. | Build the projection only from documented, versioned events; store and query it in the consuming service's own schema. It is a non-authoritative, potentially stale copy, not a substitute for source-service authorization or a way to retrieve undocumented fields. |
| **Tenant- and authorization-scoped cache** | Reduce repeated reads of data obtained through an allowed API or projection when the documented freshness requirements permit it. | The cache does not become the source of truth. Partition keys by tenant and relevant authorization context; define expiry/invalidation and stale-data behavior. Do not serve cached data after authorization is revoked or across tenants. |
| **Read-only Gateway aggregation** | Compose a Shell view from multiple documented service APIs when a concrete aggregation contract is approved. | The Gateway reads through APIs, not domain tables. Each source authorizes its own data. Document the participating services, response DTO, freshness, timeouts, failure/partial-result policy, and tenant-aware caching. Aggregation does not create a transaction or authoritative combined record. |

## Choosing a read path

- Use the source service's API when the caller needs an up-to-date value,
  must make a decision from authoritative state, or needs a result whose
  freshness is not guaranteed by an event projection. Examples include
  checking a quote reference with Quote Estimator before Bookings accepts a
  booking, or reading current payment status from Payments.
- Use an event projection only when the consumer's use case can tolerate
  documented eventual consistency and the required facts are present in
  producer-owned event contracts. For example, a consumer may maintain its
  own view of a booking or payment outcome from the corresponding events; it
  must not treat that view as the authoritative booking or payment record.
- Use Gateway aggregation only for read-only view composition. Send writes
  and domain commands to the service that owns the operation.
- Cache only after choosing an allowed source path. A cache may improve
  performance, but it does not change ownership, authorization, or
  freshness guarantees.
- If no suitable documented API or event exists, define that contract with
  the owning service before implementing the dependency. Do not infer a
  contract from table names, UI needs, or an example payload.

## Tenant, identity, and authorization requirements

- Establish tenant context from validated identity and service-to-service
  credentials, not from an untrusted request body or event field alone.
  `tenantId` is the API/event spelling; tenant-scoped PostgreSQL records use
  `tenant_id`.
- The source service independently authorizes access to its resources. A
  caller's authorization to its own records, a valid JWT, or successful
  access to one service does not grant access to another service's records.
- Scope every owner-local query, projection, and cache lookup to the
  validated tenant and applicable resource permissions. Do not fall back to
  a default tenant when context is missing or invalid.
- Do not return or project fields that the requesting principal is not
  allowed to read. Do not expose internal database models, secret values,
  credentials, or sensitive provider details through a read path.
- Event delivery is not authorization by itself. Consumers validate the
  producer, event type/version, tenant context, and documented payload
  before applying facts to their own projections.

## Prohibited read paths

- Direct reads or joins across service-owned schemas, including schemas on
  the same PostgreSQL Flexible Server.
- Shell/browser access to PostgreSQL, private service endpoints, or internal
  event subscriptions. The Shell calls the API Gateway only.
- Gateway queries against service tables or Gateway use of database access
  to bypass an owning service API.
- Treating an event payload, projection, cache, or aggregated response as
  authoritative when the source service owns the current state.
- Reconstructing undocumented data by querying a producer's schema,
  inspecting internal payloads, or relying on another service's table
  structure.
- Cross-service reads that silently broaden tenant scope, bypass resource
  authorization, or return success-shaped defaults when required data is
  missing or access is denied.

## Consistency, failures, and operations

Document the source of truth and expected freshness for every cross-component
read. API reads provide the source service's response at request time, not a
global snapshot across multiple services. Event projections are eventually
consistent and require idempotent consumption, event-version handling, and
an operational recovery path. Caches require explicit freshness and
authorization-aware invalidation.

Define timeouts and bounded retries for remote reads; retry only safe,
idempotent operations. Propagate `correlationId` and record safe telemetry.
On source failure, stale projection, missing event, or authorization denial,
follow the documented caller contract. Do not silently substitute stale,
missing, or unauthorized data with a success-shaped response.

Before adding a cross-component read, document:

1. The caller, data owner, purpose, and minimum required fields.
2. The selected path (API, event projection, cache, or Gateway aggregation)
   and its versioned contract.
3. Tenant context, authentication, resource authorization, and field-level
   exposure.
4. Freshness, consistency, timeout/retry behavior, and failure handling.
5. Projection/cache ownership, event idempotency, invalidation, and
   operational recovery where applicable.
