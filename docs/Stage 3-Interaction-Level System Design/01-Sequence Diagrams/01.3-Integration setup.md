# Integration Setup

## Purpose and status

This sequence describes how an authorized tenant administrator connects a
capability to an external provider. The service that owns the capability
owns its provider connection and behavior: for example, Payments owns
payment-provider interactions, and Notifications owns message delivery.
There is no standalone Integration Service or shared integrations schema in
the current architecture.

The specific setup route, request/response DTOs, provider verification
steps, connection states, and failure-recovery contract are not defined.
The sequence is therefore logical; provider-specific contracts must be
defined by the owning service before implementation.

## Logical sequence

```mermaid
sequenceDiagram
    autonumber
    actor Admin as Tenant administrator
    participant Shell as Control Panel Shell
    participant Gateway as API Gateway
    participant Owner as Capability-owning service
    participant Provider as External provider
    participant KeyVault as Azure Key Vault
    participant Database as Owner's PostgreSQL schema

    Note over Admin,Gateway: Administrator has an authenticated session and a valid Auth-issued JWT
    Admin->>Shell: Enter provider configuration and credentials
    Shell->>Gateway: Submit setup request over HTTPS (route/DTO TBD)
    Gateway->>Gateway: Validate JWT, establish tenant context, attach correlationId
    Gateway->>Owner: Route request with trusted identity and tenant context
    Owner->>Owner: Validate input and authorize tenant/resource operation

    alt Request is invalid or caller is unauthorized
        Owner-->>Gateway: Validation or authorization error
        Gateway-->>Shell: Canonical error envelope with correlationId
        Shell-->>Admin: Display safe error; do not retain credentials
    else Request is valid and authorized
        opt Provider verification is supported and required by its contract
            Owner->>Provider: Verify credentials or connection (provider-specific)
            Provider-->>Owner: Verification result
        end

        alt Provider verification fails
            Owner-->>Gateway: Safe provider-connection error
            Gateway-->>Shell: Canonical error envelope with correlationId
            Shell-->>Admin: Display safe failure status
        else Connection can be stored
            Owner->>KeyVault: Store credential using managed identity
            KeyVault-->>Owner: Secret reference
            Owner->>Database: Persist tenant_id, provider metadata, reference, and safe status
            Database-->>Owner: Commit result

            alt Metadata persistence succeeds
                Owner->>Owner: Record safe audit outcome
                Owner-->>Gateway: Return safe status and reference-safe identifier
                Gateway-->>Shell: Canonical success envelope with correlationId
                Shell-->>Admin: Display connection status
            else Metadata persistence fails after secret write
                Owner->>Owner: Apply documented recovery/reconciliation policy (TBD)
                Owner-->>Gateway: Dependency failure without secret details
                Gateway-->>Shell: Canonical error envelope with correlationId
                Shell-->>Admin: Display incomplete setup status
            end
        end
    end
```

The provider verification step is optional and applies only when required
and supported by the provider and owning-service contract. The sequence does
not establish whether verification occurs before or after credential
storage in every provider integration; the owner must define that ordering
and the handling of failed or ambiguous provider responses.

If Key Vault accepts a secret write but persistence of its reference fails,
the system may have an unreferenced secret. The current docs do not specify
compensation, cleanup, or reconciliation behavior. Define that policy
explicitly; do not assume a successful database rollback also removes a
Key Vault secret.

## Trust and data boundaries

- The Shell calls the API Gateway only and never calls the provider, owning
  service, database, or Key Vault directly.
- The Gateway validates the Auth-issued JWT and establishes trusted tenant
  context. The owning service independently validates that context and
  authorizes the requested connection operation. A client-supplied
  `tenantId` is not authoritative.
- The owning service persists connection metadata and the Key Vault
  reference only in its own schema. Tenant-scoped PostgreSQL records use
  `tenant_id`; API and event contracts use `tenantId`.
- The owning service accesses Key Vault through its managed identity and
  least-privilege permissions. Possession of a reference alone does not
  authorize access to a secret.
- Store credential values only in Key Vault. Do not persist them in
  PostgreSQL, browser state, API responses, events, logs, or source control.
- Return only safe connection status and a reference-safe identifier. Do not
  return the secret, Key Vault credential contents, or sensitive provider
  payloads.
- Do not share provider credentials across tenants or services unless a
  separately reviewed contract explicitly requires it.

## Failure and operational behavior

The owning API contract must define validation, authentication,
authorization, provider, Key Vault, and persistence errors using the
canonical Gateway response envelope. Errors must not expose tokens,
credentials, secret values, SQL, internal provider details, or
cross-tenant resource existence.

Propagate `correlationId` through Gateway and service operations. Record
auditable setup outcomes with actor, tenant, target connection, action, and
result while redacting credentials and sensitive provider data. Use bounded
retries and idempotency where the operation may be safely retried. Do not
repeat a provider-side operation unless its contract supports safe
deduplication or the owner can establish the prior outcome.

The service must distinguish a completed connection from a pending,
unverified, failed, or indeterminate operation if those states are needed.
The current docs do not establish the state names, retry limits, cleanup
policy, or reconciliation schedule; the owner must define them.

## After setup

For runtime provider calls, the same owning backend service resolves the
secret using its managed identity and the stored Key Vault reference. The
Shell does not retrieve or handle the secret. Rotation and disconnect are
separate lifecycle operations: the owner updates or revokes the Key Vault
value according to provider policy and updates its own safe metadata and
audit record.

## Decisions required before implementation

- Identify the owning service, provider, setup route, and exact request and
  response DTOs for each integration.
- Define credential validation and provider-verification behavior, including
  timeout and ambiguous-result handling.
- Define Key Vault reference naming, managed identity permissions, secret
  lifecycle, and cleanup/reconciliation if metadata persistence fails.
- Define tenant/resource authorization, connection states, idempotency,
  retries, audit fields, and retention.
- Specify safe error codes, response data, `correlationId` behavior, and
  redaction in logs and telemetry.
- Define rotation, revocation, disconnect, and recovery procedures for each
  provider; do not infer a generic lifecycle contract.
- Use documented, versioned APIs or events if another service needs
  connection status. Do not introduce cross-schema access or assume a
  standalone Integration Service.
