# Retry Policies

## Purpose and governing rules

Retries recover from temporary failures; they do not make a failed operation
successful, replace error handling, or establish that a timed-out write did
not commit. Apply retries only when the failure is classified as transient,
the operation is safe to repeat, and the retry fits within the caller's
remaining time budget.

Use bounded timeouts and retry attempts with backoff. Do not retry
indefinitely, retry every error, or allow each layer in a request chain to
independently multiply the same retry budget. The component that owns the
operation defines its retry behavior and documents it with the relevant API
or consumer contract.

Current `/docs` establish bounded retries, exponential backoff, idempotency
for retryable writes, at-least-once Service Bus delivery, idempotent
consumers, and dead-lettering. They do not specify numeric attempt limits,
delays, timeout budgets, or a universal HTTP status/error classification.
Set those values per operation and environment; do not infer them from
platform defaults.

## Failure classification

Classify the failure before deciding to retry:

| Failure | Retry guidance |
|---|---|
| Temporary network, service unavailability, or dependency timeout | Retry only if the operation is safe or idempotent, within bounded attempts and the end-to-end deadline. A timeout does not prove that the remote operation failed to commit. |
| Explicit throttling or rate limiting | Respect a documented retry hint such as `Retry-After` when provided; otherwise use the operation's bounded backoff policy. Do not retry sooner than the owning contract permits. |
| Validation or malformed request | Do not retry without changing the request. Return the documented validation error. |
| Authentication or authorization failure | Do not automatically retry with altered identity, tenant context, or broader credentials. Follow the authentication flow or return the documented denial. |
| Not found, conflict, or domain-state rejection | Do not assume it is transient. Retry only when the owning contract explicitly documents a recoverable condition and the state is rechecked safely. |
| Unsupported API/event version or permanently invalid message | Do not retry as a transient error. Follow compatibility, quarantine, or dead-letter procedures. |
| Unknown or ambiguous outcome of a non-idempotent write | Do not blindly repeat it. Reconcile through the owning service or provider using the documented operation/status contract. |

HTTP codes alone do not define a universal retry decision. The operation's
documented error codes, idempotency guarantees, and dependency behavior
control the classification. Do not retry caller errors just because a
generic transport library classifies them as retryable.

## Synchronous HTTP and Gateway calls

- Set a finite timeout for each downstream call and an overall request
  deadline. Per-attempt timeouts and backoff must fit within that deadline;
  stop retrying when the caller can no longer receive a useful result.
- Retry transient downstream failures only for safe reads or operations
  whose contract guarantees idempotency. The Gateway must not automatically
  retry a non-idempotent write unless the endpoint contract defines a safe
  idempotency mechanism.
- Use an idempotency key for writes that may be retried after connection
  loss, timeout, or ambiguous response. The owning service must scope and
  persist idempotency outcomes so repeated attempts do not duplicate the
  business effect. The exact key format, scope, and retention are
  endpoint-owned contract decisions.
- Do not retry a request after its outcome is ambiguous unless its
  idempotency contract makes that safe or the caller first reconciles
  through the owning service.
- Use bounded exponential backoff for eligible transient failures. Add
  jitter where supported to avoid synchronized retry bursts. Respect
  documented server retry hints without exceeding the caller's deadline.
- Avoid retry multiplication across Shell, Gateway, and service layers.
  Assign and document retry ownership for each dependency; propagate a
  deadline or remaining time budget where the contract supports it.
- A circuit breaker may stop calls to a failing dependency while it
  recovers. It complements bounded retries; it is not permission to return
  a success-shaped default or to bypass authorization.
- For a multi-service aggregate, retry only safe, idempotent downstream
  reads according to the aggregate contract. Preserve its documented
  all-or-partial failure behavior; do not silently omit failed sections.

The Shell must not treat a timeout as proof that an action failed or
succeeded. For a state-changing request, use the documented idempotency
and/or status-refresh flow before offering a retry that could duplicate the
action.

## Azure Service Bus consumers

Azure Service Bus delivery is at least once. Consumers must therefore be
idempotent even when they do not explicitly request a retry. The consumer
must validate the envelope, producer, event type/version, tenant context,
and domain preconditions before applying its own effect.

- Retry only transient processing or dependency failures, using the
  consumer's bounded backoff and delivery policy.
- Persist the consumer-owned effect and deduplication state durably before
  acknowledging the message. Use `eventId` plus a documented consumer or
  operation scope to detect duplicates.
- Do not retry permanent validation, authorization, unsupported-version,
  or domain failures indefinitely. Classify them under the consumer's
  documented poison-message policy.
- Do not repeat an ambiguous external side effect blindly. Reconcile with
  the provider or owning service using a documented reference/status
  operation before attempting it again.
- After retry exhaustion or permanent failure, dead-letter and alert
  according to the consumer's policy. Replay must preserve validation,
  tenant isolation, idempotency, and audit controls.
- Do not assume global message ordering. If processing depends on ordering,
  document the session/partition strategy and behavior for late or
  out-of-order messages.

See [02.3-Dead‑letter strategy.md](../02-Event%20Flow%20%26%20Messaging/02.3-Dead%E2%80%91letter%20strategy.md)
for failure classification, dead-letter handling, and replay constraints.

## Tenant, security, and observability

- A retry must preserve the original authenticated identity, trusted tenant
  scope, authorization decision requirements, and `correlationId`. Never
  retry under a default tenant or broaden permissions to make an operation
  succeed.
- Each service continues to authorize its own resources. A previously
  successful attempt does not authorize later retries after access or
  membership changes.
- Keep retry state and idempotency records within the owning service's
  persistence boundary. Do not write to another service's schema to
  coordinate a retry.
- Emit safe structured telemetry for the operation, dependency, attempt,
  delay, outcome category, and `correlationId`. Avoid logging tokens,
  credentials, secret values, raw sensitive payloads, or unnecessary
  cross-tenant details.
- Monitor retry volume, exhausted attempts, latency, circuit-breaker
  state, queue age, and dead-letter volume. Alert thresholds and
  escalation ownership are operational decisions that must be documented.

## Contract checklist

Before enabling retries for an operation or consumer, document:

1. Retryable and non-retryable failure categories, based on the owning
   contract rather than status codes alone.
2. The retry owner, maximum attempts, per-attempt timeout, backoff schedule,
   any server retry hints, and the overall deadline.
3. Whether the operation is idempotent; for writes, the idempotency key
   scope, persistence, duplicate response, and retention behavior.
4. How callers reconcile ambiguous write outcomes and how consumers handle
   duplicate messages and external side effects.
5. Circuit-breaker behavior, retry exhaustion, dead-letter/replay policy
   where applicable, and observable alert conditions.
6. Tenant and authorization behavior across retries, including revocation
   and safe diagnostic handling.

Until these values are defined, use bounded retries only where safety is
established; do not guess numeric limits, retry statuses, or delivery
defaults.
