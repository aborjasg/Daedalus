# Timeout Boundaries

## Purpose and status

Timeouts bound how long a caller waits for an operation or dependency. Every
synchronous request and downstream call must have a finite timeout; retries,
backoff, and all downstream work must fit within the caller's remaining
deadline.

Current `/docs` require bounded timeouts, circuit breakers, retry budgets,
and per-endpoint latency targets established through load testing. They do
not specify numeric timeout values, a universal end-to-end request budget,
or product-specific timeout configuration. Define budgets for each
operation and environment; do not infer them from framework or cloud
defaults.

## Boundary model

For a synchronous request, the caller's total deadline contains all work
performed before a response can be returned:

```text
Caller deadline
  ├── Gateway processing and policy
  ├── Service processing
  │     ├── database and other dependency calls
  │     └── bounded retry attempts and backoff
  └── response serialization and transport
```

Each nested call must have a finite timeout shorter than the time remaining
for its parent to return a useful result. A child timeout must leave enough
time for the parent to stop work, handle the error, and return the documented
response. Do not let a downstream timeout or retry schedule outlive the
upstream request deadline.

For asynchronous work, the producer's HTTP request ends when the documented
acceptance or submission response is returned; it does not bound the full
background workflow. Consumers and external providers need their own
operation timeouts, bounded retries, and recovery policies. Message expiry,
delivery locks, retry counts, and end-to-end workflow deadlines must be
defined in the owning operational contract; none has a universal numeric
value in current docs.

## Synchronous HTTP and service calls

- Set explicit finite timeouts for each outbound dependency call and a
  request-level deadline for the whole synchronous operation.
- Allocate the budget across gateway processing, service work, dependency
  calls, and response handling. Concurrent fan-out may reduce elapsed time,
  but each call still needs a bound and the aggregate deadline must cover
  the agreed response policy.
- Configure connection establishment and response/read phases separately
  where the chosen client supports it. A timeout in one phase does not
  necessarily stop work already accepted by the remote service.
- Propagate a deadline or remaining time budget between trusted backend
  components when the contract supports it. Do not trust a client-supplied
  deadline to extend server limits or bypass policy.
- A service must stop waiting on a dependency when its own deadline is
  exhausted. It must not continue unbounded work merely because the caller
  disconnected.
- The Gateway must bound each downstream request and the total aggregation
  duration. The aggregate's contract defines whether a dependency timeout
  fails the whole request or permits a clearly represented partial result;
  no generic partial-success behavior is established.
- For database and provider calls, use operation-specific limits that fit
  within the enclosing service deadline. Do not start a new retry when the
  remaining budget cannot accommodate its timeout, backoff, and response
  handling.
- Include serialization, queuing, and network transit in endpoint latency
  measurements. Establish P95 targets per endpoint through load testing
  rather than applying one assumed target to all operations.

## Retries and circuit breakers

Timeouts and retries are related but separate controls. A timeout bounds one
wait; a retry policy bounds repeated attempts. The combined attempt durations
and backoff must remain within the parent deadline. Avoid multiplying retry
budgets at the Shell, Gateway, and service layers.

Retry a timed-out operation only when it is safe to repeat or protected by
the operation's documented idempotency contract. A timeout is an ambiguous
outcome: a remote write may have committed even if the caller did not
receive its response. Use the owning service's documented idempotency or
status/reconciliation operation before repeating a potentially
non-idempotent action.

A circuit breaker can prevent calls to a failing dependency while it
recovers, but it does not replace per-call timeouts or the documented
failure response. It must not convert failure into success-shaped default
data or bypass authorization.

See [05.1-Retry policies.md](./05.1-Retry%20policies.md) for retry
classification, idempotency, backoff, and retry-exhaustion guidance.

## Asynchronous consumers and external providers

- A Service Bus consumer applies a finite timeout to each dependency or
  provider operation. The consumer owns its processing budget and must
  acknowledge only after the required effect and deduplication state are
  durable.
- If processing cannot complete within one delivery attempt, use the
  consumer's documented bounded retry and dead-letter policy. Do not extend
  waits or retry indefinitely to avoid classifying a failure.
- A lock loss, redelivery, or caller timeout does not prove that the
  consumer's effect failed. Consumers must be idempotent and reconcile
  ambiguous external side effects before repeating them.
- An API response that accepts asynchronous work does not promise that the
  workflow has completed. Return only the status and guarantees defined by
  the API contract; the caller checks subsequent state through documented
  Gateway APIs.
- Provider connection and response limits, provider idempotency, retry
  behavior, and reconciliation are owned by the service responsible for
  that integration. Do not assume one provider's timeout behavior applies
  to another.

See [02.3-Dead‑letter strategy.md](../02-Event%20Flow%20%26%20Messaging/02.3-Dead%E2%80%91letter%20strategy.md)
for retry exhaustion, dead-letter, and replay constraints.

## Client disconnects and cancellation

A browser, Shell, or upstream client timing out or disconnecting does not
prove that a request was cancelled or that a write did not commit. The
service and Gateway must distinguish caller-wait expiration from confirmed
operation cancellation:

- Stop work that can be safely cancelled when the request deadline expires,
  while respecting transaction and external-operation semantics.
- Do not claim a state-changing operation was cancelled unless the owning
  service confirms cancellation through its documented contract.
- For an ambiguous write, preserve the idempotency/reconciliation path so
  the caller can determine the outcome without duplicating the effect.
- Long-running booking, scheduling, job, payment, and notification work
  remains asynchronous through Azure Service Bus as documented; do not keep
  an HTTP request open as an implicit background-work mechanism.

## Error handling and observability

When a timeout occurs, return or propagate the documented error through the
canonical API envelope with a `correlationId`. Do not expose internal
addresses, stack traces, SQL, tokens, credentials, or raw provider details.
A timeout must not be reported as a successful result or a definitive
failure of a write when the outcome is unknown.

Record safe telemetry for the caller operation, dependency, timeout phase
where known, elapsed duration, remaining deadline, retry attempt, and
outcome. Monitor endpoint latency, dependency latency, timeouts, retry
exhaustion, circuit-breaker state, and queue age. Thresholds, alert
ownership, and retention are operational decisions and must be documented.

## Timeout contract checklist

For every synchronous endpoint and asynchronous consumer, document:

1. The caller-facing deadline and the owner of the timeout policy.
2. Finite per-dependency timeouts and how they fit within the parent
   deadline, including database and provider calls where applicable.
3. Retry attempts and backoff within the remaining budget, including
   idempotency and ambiguous-write reconciliation.
4. Behavior after client disconnect, cancellation request, dependency
   timeout, queue lock loss, or asynchronous acceptance.
5. Aggregate behavior when one dependency exceeds its deadline.
6. Safe error mapping, `correlationId` propagation, telemetry, and alert
   ownership.

Numeric values must be established through endpoint contracts, load testing,
dependency guarantees, and operational requirements. Until agreed, require
finite limits and bounded retries but do not guess a timeout duration,
latency target, or global deadline.
