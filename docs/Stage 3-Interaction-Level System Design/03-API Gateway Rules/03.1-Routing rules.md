# API Gateway Routing Rules

## Purpose and scope

The API Gateway is the sole public entry point for the Control Panel Shell,
users, external clients, and supported inbound integrations. Backend
services are private and are not directly exposed to browsers or third
parties. The Gateway routes versioned HTTPS requests to the service that owns
the requested capability; it does not own domain records or replace
service-level authorization.

The current documentation specifies the public base path and service route
families, but does not select a concrete Gateway product or define exact
endpoint paths, path rewriting, HTTP-method allowlists, or status-code
mappings. The rules below capture the documented routing contract. Do not
infer an Azure API Management deployment or product-specific configuration
from the generic term “API Gateway.”

## Public route structure

The current public API base path is `/api/v1`. Route families beneath that
base path map to the following owning services:

| Public route family | Owning service | Documented capability |
|---|---|---|
| `/api/v1/auth/*` | Auth | Sign-in/session and current identity |
| `/api/v1/customers/*` | Customers | Customer search, profile, and lifecycle |
| `/api/v1/bookings/*` | Bookings | Booking creation and status |
| `/api/v1/quotes/*` | `quotes-api` (Quote Estimator) | Quote requests and estimates |
| `/api/v1/scheduling/*` | Scheduling | Availability and assignment |
| `/api/v1/jobs/*` | Jobs | Job execution and completion |
| `/api/v1/payments/*` | Payments | Payment status, refunds, and reconciliation views |
| `/api/v1/notifications/*` | Notifications | Templates, delivery status, and preferences |

The owning service defines the endpoint paths, methods, DTOs, and domain
behavior within its route family. A route family is not authorization to
invoke every operation in that service.

Integration setup is submitted through the route of the service that owns
the integrated capability. There is no documented generic
`/api/v1/integrations/*` route or standalone Integration Service.

Quote Estimator owns tenant-specific pricing rules and estimate calculation.
Bookings owns booking lifecycle and the accepted booking-price snapshot. The
`/quotes/*` route family does not define endpoint-specific paths, methods,
request/response DTOs, or price formulas; Quote Estimator must document those
in its service API contract.

## Route matching and forwarding

- Match public requests against the explicit, documented API major-version
  prefix and a registered service route family. A request must not select a
  backend using a client-controlled hostname, header, query value, or body
  field.
- Forward each request only to the private backend that owns its matched
  capability. Do not route browser or external traffic directly to a service
  endpoint that bypasses the Gateway.
- Preserve the endpoint contract's HTTP method, path, query, and body
  semantics. Whether the Gateway strips or rewrites a route-family prefix,
  and the exact backend base paths, are not specified and must be agreed by
  the Gateway and service owners.
- Apply the endpoint's documented request-size and schema-validation
  policies. The Gateway may perform common structural validation, but the
  owning service remains authoritative for domain validation.
- Do not route based on undocumented headers, query parameters, or path
  aliases. Define any future route alias or rewrite as part of the versioned
  Gateway and service contract.
- Use health-aware backend selection. Backend pools, health probes,
  availability zones, and load-balancing algorithms are deployment
  configuration decisions not established in the current API contracts.

## Authentication, identity, and tenant context

- Terminate TLS at the public Gateway boundary and validate JWT signature,
  issuer, audience, expiry, and required claims for routes that require an
  authenticated caller.
- Apply the Auth contract's operation-specific authentication rules to
  `/api/v1/auth/*`; do not assume that unauthenticated sign-in operations
  require an existing JWT.
- Establish and propagate trusted identity, tenant context, correlation ID,
  and trace context to the target service. Do not trust a client-supplied
  `tenantId` from a body, URL, query, or header as the source of tenant
  authorization.
- The Gateway performs coarse authentication and policy checks. The target
  service independently validates trusted identity context and enforces
  tenant and resource authorization for its own data.
- A valid JWT, successful route match, visible Shell navigation item, or
  Gateway authentication result alone does not grant access to a tenant or
  resource.
- Do not forward credentials or tokens to unrelated backends. Propagate only
  the identity and context required by the documented downstream contract.

## Cross-cutting Gateway behavior

For a matched request, the Gateway:

1. Applies TLS, CORS, WAF, rate-limit, and request-size policies configured
   for the public API.
2. Validates the route and applies the appropriate authentication and
   coarse-policy checks.
3. Establishes or propagates `correlationId`, trace context, and trusted
   tenant context.
4. Routes to the private owning service using health-aware load balancing.
5. Returns the canonical response envelope and translates downstream
   failures without exposing raw internal responses.

The canonical response envelope is:

```json
{
  "success": true,
  "data": {},
  "errors": [],
  "correlationId": "corr-123"
}
```

On failure, `success` is `false`; `data` is `null` in the documented error
example; and each error item contains `code`, `message`, and `details`.
Endpoint owners define their stable codes and any structured `details`.
Exact HTTP status mappings are not specified by current docs and must be
defined consistently by the Gateway and owning services.

## Versioning and route evolution

- Public routes use a major version in the path: `/api/v1/{service-route}`.
- Keep the major version consistent across all documented route families.
- Introduce a new major path such as `/api/v2` for an incompatible public
  contract change. Do not silently change a published `/api/v1` route's
  meaning or behavior.
- Compatible additions must follow the API versioning and endpoint schema
  rules; do not use query parameters or undocumented headers to signal
  versions.
- When changing a route or shared behavior, involve the owning service,
  Gateway, Shell, and known external consumers. Document migration and
  retirement before removing an existing route.
- Deprecation headers, notice periods, overlap duration, and retirement
  authority are not defined by current docs and must be set by Gateway
  operational policy.

## Resilience, aggregation, and caching

- Enforce bounded timeouts, circuit breakers, and exponential backoff for
  downstream calls.
- Retry only operations known to be safe or idempotent. Do not automatically
  retry non-idempotent writes unless the endpoint contract defines safe
  idempotency behavior.
- Translate downstream failures into the canonical error envelope without
  returning raw upstream bodies, stack traces, SQL, internal hostnames, or
  provider details.
- The Gateway may aggregate read-only responses where useful, but does not
  become the source of truth or transfer service ownership. Aggregation must
  preserve each target service's authorization and tenant boundaries.
- Do not cache tenant-sensitive responses without tenant-scoped cache keys
  and authorization-aware invalidation. The current docs do not prescribe
  cache duration or policy for specific routes.
- The Gateway does not publish domain events on behalf of services. Services
  publish events only after durable persistence using the documented
  messaging contracts.

## Unmatched and unsupported requests

The current docs do not define exact behavior or status codes for unknown
route families, unsupported methods, malformed version prefixes, or
unavailable backends. The Gateway contract must define these cases and return
the canonical error envelope. Unmatched requests must fail safely; they must
not fall through to a default service, reveal private backend addresses, or
expose whether a cross-tenant resource exists.

Do not return a success-shaped fallback when routing or downstream
processing fails. Include a `correlationId` for safe diagnostics and keep
internal failure details in protected server-side telemetry.

## Route ownership and contract checklist

Before adding or changing a public route, document:

- The owning service and capability, route family, HTTP method, path, and
  supported API major version.
- Authentication requirements, required permissions, tenant-context
  behavior, and service-side resource authorization.
- Request and response DTOs, validation, error codes/details, and status
  mappings.
- Backend target and any prefix rewrite, path normalization, or method
  restrictions.
- Request-size, rate-limit, CORS, WAF, timeout, retry, circuit-breaker, and
  idempotency behavior.
- `correlationId` and trace propagation, caching policy, and safe downstream
  error translation.
- Consumer compatibility, version migration, deprecation, and retirement
  plan if an existing route changes.

Until endpoint-specific routing contracts are approved, expose only the
documented route families and use the owning service's documented API
contract. Do not invent generic routes for modules, feature toggles,
platform billing, or integrations. Quote Estimator uses the documented
`/quotes/*` family; its endpoint details remain service-owned.
