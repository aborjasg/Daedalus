# API Gateway Authentication and Authorization Rules

## Purpose and boundaries

Auth is the authoritative service for user authentication, identity, tenant
memberships, roles, permissions, and short-lived signed JWT issuance. The API
Gateway is the sole public entry point and validates authentication before
routing protected requests to private services.

Authentication confirms the caller's identity. It does not, by itself,
authorize access to a tenant, module, or resource. The Gateway performs
coarse authentication and policy checks; each target service independently
enforces tenant and resource authorization for its own data.

The public Auth route family is `/api/v1/auth/*`. Exact sign-in, sign-out,
current-identity, identity-provider callback, and renewal endpoint paths and
payloads must come from the Auth/Gateway contract. Do not infer new endpoints
or behavior from the route family.

## Route authentication policy

- Apply the endpoint's documented authentication requirement before routing.
  Protected route families require an authenticated caller; documented
  sign-in and other explicitly public Auth operations must remain reachable
  without an existing JWT.
- Do not treat every route under `/api/v1/auth/*` as either public or
  protected by default. Auth endpoint owners must specify the policy for
  each operation.
- Do not bypass JWT validation for a protected endpoint because the request
  came from the Shell, an expected network, or a previously authenticated
  page.
- Route a successfully authenticated request only to its owning private
  service. The Gateway does not use a client-provided identity, tenant, or
  role value to select a privileged backend or policy.
- Backend services are never directly exposed to browsers or external
  clients. The Shell calls the Gateway only.

## JWT validation

For protected requests, the Gateway validates the Auth-issued signed JWT
before routing. The documented minimum validation includes:

- Signature against the trusted Auth signing key.
- Issuer and audience.
- Expiration and any required time constraints.
- Required claims defined by the Auth/Gateway identity contract.

Reject missing, malformed, invalid, expired, or otherwise unacceptable
credentials as unauthenticated. Do not accept a token merely because it can
be decoded; signature and claim validation are required. Use only approved
algorithms and trusted key configuration from the Auth contract.

The current docs do not specify exact claim names, issuer/audience values,
clock-skew allowance, signing algorithm, key-discovery mechanism, key
rotation overlap, or token lifetime. These values must be specified by the
Auth/Gateway contract and configured consistently; do not invent defaults.

## Identity, tenant, and authorization context

- Auth is authoritative for user identity and tenant membership. A user may
  have tenant-scoped membership and roles; global roles must not substitute
  for an authorized tenant context.
- The Gateway establishes or propagates trusted identity, tenant context,
  `correlationId`, and trace context to the target service according to the
  documented contract.
- A `tenantId` supplied by a client in a path, query, header, or request body
  is not authoritative. If an endpoint accepts such a field for a
  documented reason, the Gateway and owning service validate it against the
  trusted identity context.
- Roles and permissions are managed by Auth. A valid JWT, role claim, or
  coarse Gateway policy decision does not grant access to every resource.
- Each target service independently checks tenant and resource authorization
  for its data and operations. Services do not rely on the Gateway as their
  only authorization boundary.
- Module visibility and client-side permission checks are presentation only.
  Direct URLs and API requests receive the same backend checks.
- Service identities and automation use the documented service-to-service
  identity mechanism and least privilege. A user JWT is not a substitute for
  a managed identity, and a service identity does not imply user permissions.

## Auth and tenant switching flows

The Shell completes sign-in or the configured identity-provider flow only
through the documented Auth/Gateway contract. Auth supports internal user
accounts and optional external identity providers; exact provider protocols,
callback routes, and account-linking behavior are not established here.

After sign-in, Auth issues a short-lived signed JWT according to its identity
contract. The Shell obtains current-identity information through the
documented `/api/v1/auth/*` contract and uses it only for authorized
presentation. When a user changes tenant context, the Shell uses the
supported Auth or Gateway operation and refreshes tenant-sensitive views.
The Gateway and target service validate the resulting context for each
request; the Shell must not switch tenant by changing a client field alone.

## Token handling and session security

- Send JWTs only using the authentication mechanism defined by the
  Auth/Gateway contract. Never put access tokens, refresh tokens, passwords,
  or credentials in URLs.
- Keep access tokens short-lived and use them only for requests to the API
  Gateway.
- Do not place tokens in page markup, browser logs, analytics, or
  client-side persistent storage such as `localStorage`.
- Select and document one token-custody pattern for the Shell. If a
  server-side session is used, keep tokens server-side and use a
  `Secure`, `HttpOnly` cookie with an appropriate `SameSite` policy. If the
  approved design requires direct browser-to-Gateway calls, follow the
  approved browser OAuth/OIDC flow and minimize token exposure.
- Protect cookie-authenticated state-changing requests against CSRF.
- Redact authentication material from logs, traces, telemetry, and error
  reporting.
- Do not infer refresh-token issuance or renewal support. If renewal is
  supported, use only its documented flow and failure behavior.
- On sign-out, invoke the documented Auth/Gateway operation when available,
  clear Shell session state, and remove locally retained authentication
  material. Do not assume that client-side clearing revokes a token unless
  the Auth contract specifies revocation.

## Failure behavior and response envelope

Authentication failures and authorization denials are distinct:

- **Unauthenticated:** credentials are missing, invalid, expired, or
  revoked. The Shell follows the documented sign-in flow and must not retry
  indefinitely with the same token.
- **Forbidden:** the caller is authenticated but not authorized for the
  operation, tenant, or resource. The Shell displays access denied rather
  than treating it as a sign-in failure.
- **Unavailable Auth/Gateway:** show a recoverable failure. Do not treat a
  timeout or dependency failure as successful authentication.

The Gateway returns the canonical envelope:

```json
{
  "success": false,
  "data": null,
  "errors": [
    {
      "code": "AUTHENTICATION_ERROR",
      "message": "Authentication is required.",
      "details": {}
    }
  ],
  "correlationId": "corr-123"
}
```

The error code and message above are illustrative, not an established
Auth error catalog. Auth and endpoint owners define stable codes and safe
messages. The Gateway translates downstream failures without exposing raw
service responses. Do not disclose tokens, credentials, SQL, stack traces,
internal hostnames, sensitive claims, or whether a resource exists in
another tenant. Exact HTTP status mappings are not specified in current
docs and must be defined by the Gateway and service contracts.

## Gateway security and resilience

- Terminate TLS at the public Gateway and keep backend services private.
- Apply the documented WAF, CORS, rate-limit, request-size, and schema
  validation policies without allowing them to replace service-side
  authorization.
- Do not automatically retry authentication or authorization failures.
  Retry transient downstream failures only within bounded timeout and
  backoff policy and only when the operation is safe or idempotent.
- Do not cache authentication-sensitive or tenant-sensitive responses
  without tenant-scoped keys and authorization-aware invalidation.
- Propagate `correlationId` and trace context for protected diagnostics.
  Correlation identifiers are not credentials or authorization evidence.

## Auditing and observability

The responsible backend components audit authentication failures,
authorization denials, role/permission changes, and administrative identity
changes. Where applicable, audit records identify actor, tenant, target,
decision, and `correlationId`. Record safe outcomes without storing tokens,
passwords, credentials, or unnecessary sensitive identity data.

Gateway and Auth telemetry must support tracing across services while
redacting authentication material. The Shell may record route, outcome, and
`correlationId` for diagnostics, but must not duplicate token contents or
sensitive identity data into client-visible logs.

## Contract decisions before implementation

The Auth/Gateway contract must document:

- Which Auth operations are public and which require an authenticated
  caller, including sign-in, sign-out, current identity, and any supported
  identity-provider callbacks.
- JWT issuer, audience, signing algorithm and trusted-key configuration,
  required claims, expiry, clock-skew handling, and key-rotation behavior.
- Supported identity providers, account-linking rules, and sign-in failure
  behavior.
- Tenant selection and context propagation, membership checks, and any
  tenant-switch operation.
- Role/permission claim or lookup behavior and how trusted authorization
  context reaches each target service.
- Token custody in the Shell, renewal/revocation support, session behavior,
  cookie settings, and CSRF protections where applicable.
- Authentication/authorization error codes, safe messages, HTTP status
  mappings, rate limits, and audit requirements.

Until these contracts are specified, do not invent claim names, endpoint
paths, token renewal behavior, or a client-controlled tenant mechanism.
