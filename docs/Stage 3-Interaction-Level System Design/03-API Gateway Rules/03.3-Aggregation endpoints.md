# API Gateway Aggregation Endpoints

## Purpose and status

The API Gateway may aggregate read-only responses where useful to provide
view data to the Control Panel Shell. Aggregation is a presentation-oriented
composition of service-owned API results; it does not make the Gateway a
domain service, persistence owner, or authorization authority.

The current `/docs` route inventory defines service route families but no
specific aggregation endpoint, combined response DTO, fan-out plan,
partial-result policy, or cache policy. This document defines constraints
for any future aggregation endpoint. It does not establish new paths or
promise that a particular aggregate is implemented.

## Ownership and eligibility

- Aggregate only read-only responses. Commands and writes are routed to the
  service that owns the operation; do not turn a Gateway aggregate into a
  multi-service write or workflow orchestrator.
- The Gateway may compose data from documented service APIs. Services do
  not read one another's PostgreSQL schemas, and the Gateway must not query
  domain tables directly.
- The target service remains the source of truth for its records and
  enforces tenant and resource authorization. Gateway aggregation does not
  weaken or replace those checks.
- The Shell calls the Gateway only. It must not call private services
  directly or subscribe to internal events to build a view.
- Event payloads are not substitutes for service API response contracts.
  The Shell and Gateway must not infer a view DTO from internal event or
  database schemas.

## Route and response contract

No aggregation route is currently defined. Before exposing one, document
its versioned public path, HTTP method, owning Gateway responsibility,
participating services, authentication requirements, request parameters,
and response DTO. Do not invent a generic `/dashboard`, `/overview`, or
cross-domain path based only on this guidance.

An aggregate response must:

- Use the canonical API envelope:

  ```json
  {
    "success": true,
    "data": {},
    "errors": [],
    "correlationId": "corr-123"
  }
  ```

- Define a stable, caller-facing `data` DTO rather than returning raw
  downstream response bodies or internal service models.
- Include only fields needed by the documented view and authorized for the
  caller. Do not expose database schemas, internal event payloads, secret
  values, sensitive provider details, or cross-tenant records.
- Preserve the meaning of each source service's data. Do not silently
  transform an unavailable, missing, or unauthorized result into a
  success-shaped default.
- Document freshness and consistency expectations if the aggregate combines
  values read at different times. A read-only aggregate is not a
  cross-service transaction or a globally consistent snapshot.

The exact DTO and field-level transformation rules belong in the endpoint
contract and must be versioned with the API.

## Authentication, authorization, and tenant isolation

- Authenticate the request according to the route contract. The Gateway
  validates the Auth-issued JWT and establishes trusted identity and tenant
  context before calling downstream services.
- Never use a client-supplied `tenantId` as the source of authorization.
  API/event contracts use `tenantId`; tenant-scoped PostgreSQL records use
  `tenant_id`.
- Each downstream service independently authorizes access to its own
  resources in the trusted tenant context. A Gateway-level check, successful
  call to one service, or valid JWT does not grant access to another
  service's data.
- If a participating service rejects the caller or tenant context, the
  aggregate must not include protected data from that service. The endpoint
  contract must define whether the entire request fails or a documented
  partial result is safe; do not silently omit protected fields.
- Do not cache an aggregate across tenants or authorization contexts.
  Tenant-sensitive cache keys and authorization-aware invalidation are
  required if caching is explicitly enabled.

## Downstream calls and failure behavior

For each dependency, document timeout, circuit-breaker, and retry behavior.
Use bounded timeouts and retries; retry only safe/idempotent read operations
and only according to the Gateway resilience policy. Do not retry caller
validation, authentication, or authorization failures.

The contract must explicitly decide whether downstream failure causes:

1. A failure for the entire aggregate, returned in the canonical error
   envelope; or
2. A partial success with clearly documented unavailable sections and
   corresponding status metadata in the endpoint DTO.

The current API envelope and service contracts do not define a generic
partial-success convention. Do not return `success: true` with missing or
defaulted data unless the endpoint contract explicitly defines that behavior
and how clients distinguish incomplete results. Do not add undocumented
top-level envelope fields to indicate partial failure.

When returning a failure, preserve the downstream failure meaning where
appropriate, translate it into the canonical envelope, and avoid returning
raw upstream bodies, stack traces, internal hostnames, SQL, or provider
details. Include `correlationId` for safe diagnostics. Exact HTTP status
mappings remain a Gateway/service contract decision.

## Aggregation and consistency limits

- Prefer the smallest set of documented read operations needed for the view.
  Do not fetch unrelated data or retrieve complete records merely to discard
  fields after aggregation.
- The current docs do not prescribe parallel versus sequential fan-out,
  maximum downstream call count, payload limits, or aggregate latency
  budgets. Specify these for each endpoint and apply bounded resource limits.
- Do not imply a transactional snapshot across services. Each service owns
  its state and may observe a different commit time.
- If the view needs an asynchronous or long-running calculation, expose
  documented operation status through the owning API rather than holding an
  aggregate request open indefinitely.
- Do not publish domain events from the Gateway. Domain services publish
  events only after their own durable persistence.

## Observability and privacy

Propagate `correlationId` and trace context across the Gateway and
downstream calls. Record which dependencies succeeded or failed, timing,
and safe error classifications. Do not log complete aggregate payloads by
default; redact credentials, tokens, secret values, sensitive identity data,
and unnecessary customer or financial data.

The Gateway should expose only the data and error details needed by the
caller. Internal downstream topology and authorization details remain in
protected telemetry, not in the public response.

## Contract checklist

Before adding an aggregation endpoint, document:

- Its purpose, versioned route, method, owner, and intended Shell view.
- Participating services and the specific documented read APIs called.
- Request and response DTOs, including freshness, consistency, and any
  partial-result representation.
- Authentication, trusted tenant-context propagation, and independent
  downstream authorization expectations.
- Downstream timeout, retry, circuit-breaker, concurrency, payload-size,
  and latency limits.
- Error translation, HTTP status mapping, and behavior when each dependency
  is unavailable or denies access.
- Cache use, tenant-scoped keys, freshness, and authorization-aware
  invalidation, if caching is enabled.
- `correlationId` propagation, operational metrics, and data redaction.

Until a specific route and DTO are approved, treat Gateway aggregation as an
allowed architectural capability only. The current service route families
remain the documented public routes; no new aggregate endpoint is implied by
this document.
