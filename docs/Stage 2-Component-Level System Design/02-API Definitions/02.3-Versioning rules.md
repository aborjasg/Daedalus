# API and Event Versioning Rules

## Purpose and ownership

The API Gateway exposes versioned HTTPS routes and is the only external entry
point for the Control Panel Shell and external clients. The current public API
base path is `/api/v1`. Each service owns the request, response, and domain
error contracts for its endpoints; the Gateway routes requests and returns
the canonical `{success,data,errors,correlationId}` envelope.

These rules define how API and event contracts evolve while allowing clients
and consumers to move forward safely. An owning service proposes and documents
changes to its contract. The Gateway and affected consumers must be included
when a change affects routing, shared envelopes, or cross-service behavior.

## API version identification

- Include the API major version in the path, as in `/api/v1/{service-route}`.
- Keep the version consistent across route families at the Gateway. The
  documented route families are `/auth/*`, `/customers/*`, `/bookings/*`,
  `/scheduling/*`, `/jobs/*`, `/payments/*`, and `/notifications/*` beneath
  `/api/v1`.
- Introduce a new major path, such as `/api/v2`, when an incompatible public
  contract change is required. Do not silently change the meaning or shape of
  a published `/api/v1` operation.
- Do not use a path version to represent routine compatible additions.
- The documentation does not currently specify minor/patch version signaling,
  content negotiation, or a policy for versioning private east-west APIs.
  These must be agreed before those mechanisms are introduced; clients must
  not infer version support from undocumented headers or query parameters.

## Compatible and breaking API changes

A change is compatible only when existing documented clients can continue to
make the same requests and interpret responses with the same meaning.

Examples that are generally compatible, subject to the endpoint's documented
unknown-field and optional-field behavior:

- Adding a new endpoint without changing existing routes or shared behavior.
- Adding an optional request field that does not alter the behavior of
  requests that omit it.
- Adding an optional response field while existing field names, types, and
  meanings remain unchanged.
- Adding a new error code for a newly documented failure case, provided
  clients handle unknown codes safely and existing cases retain their meaning.
- Adding an event type or optional event field without changing existing
  event meanings or consumer requirements.

Examples of breaking changes that require a new major API version or a
separately agreed migration:

- Removing or renaming a route, request field, response field, or error code.
- Changing a field's type, format, nullability, requiredness, or meaning in a
  way that invalidates an existing client.
- Changing the meaning or outcome of an existing operation or error code.
- Requiring a request field that was previously optional or changing the
  behavior of requests that omit it.
- Changing the canonical response envelope, including field names or their
  established success/failure semantics.
- Tightening validation or authorization in a way that rejects requests
  previously accepted under the published contract. Security fixes must still
  be applied, but their compatibility impact must be communicated and
  mitigated where possible.
- Changing pagination, ordering, retry, idempotency, or asynchronous status
  behavior where existing clients depend on the documented behavior.

This list is guidance, not a substitute for checking actual consumer
assumptions. Whether adding fields is safe depends on the published
serialization rules and client behavior; endpoint contracts must specify how
unknown fields are handled.

## Major-version lifecycle

When a breaking change cannot be avoided:

1. Define and document the new versioned contract, including request and
   response schemas, errors, authorization, and behavior.
2. Keep the previous version available during an agreed migration period when
   operationally and securely feasible. A new version does not by itself
   authorize silently disabling the old one.
3. Migrate the Control Panel Shell and known external consumers, and validate
   compatibility with contract tests before switching traffic.
4. Communicate the old version's deprecation and planned retirement to
   affected consumers. Provide migration guidance and a support contact or
   correlation path.
5. Retire the old version only after the owner has reviewed consumer usage,
   completed the agreed notice period, and approved removal.

The current documentation does not define deprecation headers, notice
periods, support windows, version overlap duration, or retirement authority.
Set these in the Gateway's operational policy before announcing a version
retirement. Do not invent a universal sunset period in an endpoint contract.

## Shared envelope and error compatibility

All API versions use their documented canonical response envelope. For the
current contract:

```json
{
  "success": true,
  "data": {},
  "errors": [],
  "correlationId": "corr-123"
}
```

Each failure error item contains `code`, `message`, and `details`. Keep the
envelope stable within a major version. Error codes are machine-readable
contract elements: do not reuse a code for a different condition or change
its meaning in place. Clients use `code`, not message text, for control flow;
messages may be clarified while remaining safe and user-appropriate.

New codes and endpoint-specific `details` shapes must be documented. Clients
must handle unknown codes without crashing or misclassifying the failure.
Error details must not expose tokens, credentials, secret values, SQL,
internal implementation details, or cross-tenant resource existence.
Any change to envelope structure or established code semantics is a breaking
change.

HTTP status mappings are not yet defined consistently in the current API
documentation. The Gateway and service owners must specify the mapping for
each version and keep it consistent; a client must not infer status behavior
from examples alone.

## Schema and serialization compatibility

- Treat API DTOs as public contracts independent of PostgreSQL schemas and
  internal service models.
- Document field names, types, formats, required/optional/null behavior,
  constraints, defaults, and unknown-property behavior for each endpoint.
- Preserve the meaning of existing fields. Introduce a new field rather than
  overloading an existing field with different semantics.
- Use `tenantId` in API and event contracts and `tenant_id` in PostgreSQL.
  Tenant context from the client is never authoritative; backend components
  validate it against trusted identity context.
- Keep API request/response schemas separate from internal event schemas.
- Do not expose secret values, internal event payloads, database structures,
  or data the caller is not authorized to access.

## Event versioning

Azure Service Bus event contracts are versioned and backward compatible
during rollout. Events use the documented envelope, including `eventId`,
`eventType`, `occurredAt`, `correlationId`, `tenantId`, `sourceService`, and
`payload`. Services publish events after durable persistence; the Gateway
does not publish domain events on a service's behalf.

- Preserve the meaning of an existing event type and its fields.
- Prefer additive optional fields that existing consumers can ignore.
- Do not make a previously optional field required or change field meaning,
  type, or serialization in place when existing consumers could break.
- For an incompatible event change, define a new versioned event contract and
  migration plan. The event naming or metadata mechanism for expressing that
  version is not specified by current docs and must be agreed by producers and
  consumers.
- Producers and consumers must use contract tests and tolerate at-least-once
  delivery. Consumers remain idempotent; retries and dead-lettering follow
  the messaging contract.
- Never publish secret values or sensitive credential material in an event.

An HTTP API major version and an event schema version are independent. A new
API route version does not automatically version an event, and a new event
version does not automatically change an HTTP API.

## Change review and release checklist

Before releasing a contract change, the owning service and Gateway should
verify:

- Whether the change is compatible with every known client or consumer.
- That the route's major version and the event's version mechanism, where
  relevant, are correct and explicitly documented.
- Request and response schemas, safe error codes/details, HTTP status
  mappings, and authorization/tenant behavior remain consistent.
- Consumer contract tests pass, including old-client behavior for additive
  changes and migration behavior for breaking changes.
- The Shell and external consumers have a rollout, observability, and
  rollback plan appropriate to the change.
- Deprecation and retirement notices follow the agreed Gateway policy.

Exact deprecation timelines, HTTP status mappings, event-version notation,
private service API versioning, and automation tooling remain operational
decisions not established by the current `/docs` contracts.
