# Request and Response Schemas

## Scope and ownership

The API Gateway is the only external entry point for the Control Panel Shell
and external clients. Public operations use the explicit `/api/v1` API version
and route to the service that owns the requested capability. This document
defines the common JSON envelope and cross-cutting schema rules. Each service
owns the request and response DTOs for its own endpoints.

The current documentation defines route families for Auth, Customers,
Bookings, Scheduling, Jobs, Payments, and Notifications. It does not define
endpoint-specific request bodies, response DTOs, field constraints, or HTTP
status mappings. Do not infer those contracts from database columns, internal
events, or this document; define them in the owning service's API contract.

## Request conventions

- Use JSON request bodies for operations that accept a body. A request without
  a body must not be given an invented empty object.
- Send the short-lived Auth-issued JWT to the Gateway using the agreed
  authentication mechanism. Never put credentials or tokens in the URL or
  request body unless an explicitly documented Auth flow requires it.
- Propagate the `correlationId` using the agreed correlation header. The
  precise header name and behavior when one is absent must be specified by
  the Gateway contract.
- The Gateway establishes trusted `tenantId` context from the validated
  identity. If an API schema includes a `tenantId` for a documented reason,
  the Gateway and owning service must validate it against that trusted
  context; a client-supplied value is not authoritative.
- Validate request shape and constraints at the Gateway where appropriate
  and again in the owning service. The service is authoritative for domain
  validation and resource authorization.
- Define required, optional, nullable, format, length, range, and
  unknown-property behavior in each endpoint schema. Do not assume that
  omitted, `null`, and empty values are interchangeable.
- Use an idempotency key for commands that may be safely retried, as specified
  by the owning endpoint contract. The key's location, scope, and retention
  must be defined there.

### Endpoint-specific request example

The shape below is a documentation template, not a payload schema to copy.
Replace the placeholder with the fields defined by the owning service:

```json
{
  "fieldDefinedByOwningService": "value"
}
```

Do not add database-only fields, internal event payloads, or fields for
cross-tenant access to a public request DTO.

## Common response envelope

Every API response uses the Gateway envelope:

```json
{
  "success": true,
  "data": {},
  "errors": [],
  "correlationId": "corr-123"
}
```

The fields are:

| Field | Contract |
|---|---|
| `success` | Boolean outcome indicator. `true` for a successful response; `false` when the request failed. |
| `data` | Present on success and contains the endpoint's documented response DTO. The Gateway's error example uses `null` on failure. |
| `errors` | Array of error items. Empty on success; contains one or more errors on failure. |
| `correlationId` | Correlation identifier used to trace the request across the Gateway and services. |

Successful responses use the same envelope regardless of the owning service.
The `data` value is service- and endpoint-specific and must contain only
user-facing/API-contract data, not a database schema, secret value, or
internal event payload.

### Successful response example

```json
{
  "success": true,
  "data": {
    "resultDefinedByOwningService": {}
  },
  "errors": [],
  "correlationId": "corr-123"
}
```

The `resultDefinedByOwningService` property is illustrative only. Actual
response fields must be defined by the endpoint contract.

### Failed response example

```json
{
  "success": false,
  "data": null,
  "errors": [
    {
      "code": "BOOKING_NOT_FOUND",
      "message": "Booking was not found.",
      "details": {}
    }
  ],
  "correlationId": "corr-123"
}
```

Every error item has `code`, `message`, and `details`. `details` may be an
empty object. Error codes and messages are defined by the Gateway error model
and owning service; the example code is illustrative and does not define a
complete error catalog. Error responses must not disclose tokens, credentials,
secret values, SQL, internal implementation details, or cross-tenant resource
existence.

## Schema and serialization rules

- Keep API DTOs independent of PostgreSQL schemas and internal service models.
  Do not expose table or column names as a substitute for a stable API
  contract.
- Use `tenantId` in API and event contracts and `tenant_id` in PostgreSQL.
  API tenant context is trusted only after backend validation.
- Keep response DTOs limited to the information a caller is authorized to
  receive. Gateway aggregation does not change domain ownership or
  authorization responsibility.
- Never include secret values in request examples, response `data`, errors,
  events, or logs. Integration setup responses may return connection status
  and a reference-safe identifier only.
- Document enum values and compatibility behavior whenever an endpoint
  introduces a finite set of states. Do not expose internal implementation
  states unless they are part of the documented user-facing contract.
- Version API routes explicitly. Changes to endpoint-specific field
  requirements and compatibility follow the API versioning rules.
- Keep event schemas distinct from HTTP request/response schemas. Services
  publish domain events after durable persistence; the Gateway does not
  publish them on a service's behalf.

## Contract completeness checklist

Before an endpoint is exposed through the Gateway, its owning service contract
must specify:

- HTTP method, versioned route, authentication expectations, and authorization
  owner.
- Request body and path/query parameters, including types, constraints,
  required/optional/null behavior, and validation errors.
- Successful `data` shape, including field meanings, formats, and any
  asynchronous operation status.
- Error codes and safe messages, including validation, authentication,
  authorization, not-found, conflict, and dependency failure behavior where
  applicable.
- HTTP status mapping, content type, idempotency and retry behavior, and
  correlation-ID behavior.
- Tenant context rules and any sensitive-data handling requirements.

Exact HTTP status mappings, header names, date/time formats, pagination
conventions, and endpoint-specific DTOs are not specified by the current
`/docs` API contracts and must be settled by the Gateway and owning services.
