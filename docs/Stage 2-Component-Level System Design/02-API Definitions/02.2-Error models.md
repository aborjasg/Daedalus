# API Error Model

## Purpose and ownership

The API Gateway returns one canonical response envelope for successful and
failed API calls. This document defines the shared error shape, broad error
categories, and handling rules. The Gateway owns errors it detects while
validating or routing a request; the target service owns domain validation,
authorization, and resource errors for its capability. The Gateway translates
downstream failures into the canonical envelope without changing their
meaning or exposing internal details.

This is a common model, not a complete error-code catalog. Each endpoint's
owning service must document its stable error codes, safe messages, and
endpoint-specific details. Exact HTTP status mappings are not yet specified
by the current API documentation and must be established by the Gateway and
service contracts.

## Canonical failure envelope

```json
{
  "success": false,
  "data": null,
  "errors": [
    {
      "code": "BOOKING_NOT_FOUND",
      "message": "Booking was not found.",
      "details": {}
    }
  ],
  "correlationId": "corr-123"
}
```

The envelope fields are:

| Field | Contract |
|---|---|
| `success` | `false` when the API request failed. |
| `data` | `null` in the Gateway's documented failure example. |
| `errors` | One or more error items; each has `code`, `message`, and `details`. |
| `correlationId` | Correlates the request across the Gateway and services and supports safe diagnostics. |

`details` may be an empty object. When an endpoint needs structured details,
its contract must define the shape and permitted contents. Do not add
undocumented top-level fields to the envelope.

## Error categories

Use stable, machine-readable codes that describe the failure category or
specific failure. The following categories are guidance; each endpoint must
publish the codes it actually returns.

| Category | Meaning | Expected caller behavior |
|---|---|---|
| Request validation | The request is malformed or violates a documented field or domain constraint. | Correct the request; do not retry unchanged input. |
| Unauthenticated | Authentication is missing, invalid, expired, or revoked. | Follow the documented Auth flow; do not repeatedly retry the same invalid token. |
| Forbidden | The authenticated caller is not authorized for the operation or resource. | Show an access-denied state; do not treat it as a sign-in failure. |
| Not found | The requested resource is unavailable to the caller. | Show a safe not-found result. Do not reveal whether a cross-tenant resource exists. |
| Conflict | The request conflicts with current resource state or a concurrency constraint. | Refresh state or resolve the conflict before retrying, as the endpoint contract directs. |
| Rate limited | A request exceeded an applicable traffic limit. | Retry only according to the documented backoff guidance. |
| Dependency or service unavailable | The Gateway or a downstream dependency cannot currently complete the request. | Show a recoverable failure; retry only within bounded policy and when the operation is safe or idempotent. |
| Internal error | An unexpected failure prevented the request from completing. | Present a generic failure with the correlation ID as a support reference; do not expose implementation details. |

Authentication and authorization are distinct: a valid JWT does not grant
access to every tenant or resource. The Gateway performs coarse authentication
and policy checks, while every target service enforces tenant and resource
authorization for its own data.

## Error item fields

| Field | Contract |
|---|---|
| `code` | Stable machine-readable identifier. Clients may use it for control flow; they must not parse `message` to determine behavior. |
| `message` | Safe, concise, user-appropriate description. It must not contain internal diagnostics or sensitive data. |
| `details` | Structured endpoint-defined context, or `{}` when no safe structured context is available. |

Codes are part of the API contract. Do not silently change a code's meaning or
reuse it for an unrelated condition. Human-readable messages may be clarified
without changing the code, but must remain safe and actionable. The precise
naming convention and compatibility policy for error codes must be agreed
with the API versioning rules.

## Safe details and information disclosure

Error responses must never include:

- Access or refresh tokens, passwords, credentials, or Key Vault secret values.
- SQL, stack traces, internal hostnames, dependency credentials, or
  implementation details.
- Sensitive provider payloads or internal event payloads.
- Data that confirms the existence or state of a resource in another tenant.

For field validation, `details` may identify invalid field names and safe
validation constraints only when the endpoint contract defines that format.
Do not echo sensitive submitted values. For unexpected failures, return a
generic message and use `correlationId` to locate protected server-side
diagnostics.

## HTTP status and envelope consistency

The API response envelope and HTTP status code serve different purposes: the
envelope communicates the API-level outcome; the HTTP status communicates the
transport-level result. The current documentation establishes the envelope but
does not specify status codes for individual error categories. The Gateway
and owning service contracts must define and test those mappings consistently.

The Gateway must translate downstream failures into the canonical envelope.
Infrastructure or protocol failures must not leak raw downstream responses to
the caller. If a request fails, the returned `success` value and `errors`
content must agree with the failure; the API must not return a success-shaped
fallback for an unsuccessful operation.

## Retries and asynchronous outcomes

- Do not automatically retry validation, authentication, authorization, or
  other caller-correctable errors.
- Retry transient dependency failures only within bounded timeout and
  backoff policy. The Gateway retries only operations known to be safe or
  idempotent.
- Writes that may be retried require the endpoint's documented idempotency
  behavior. Do not retry a non-idempotent operation merely because the
  caller timed out; its outcome may be unknown.
- A successfully accepted asynchronous operation is not an API error solely
  because its later business outcome is failed. Return the documented
  operation/status DTO and let the Shell render the state. Report an API
  error when the request itself could not be accepted or processed according
  to its contract.
- Service Bus delivery failures, retries, and dead-letter handling are
  internal messaging concerns. They must be observable and surfaced through
  documented status APIs where applicable, not as raw queue or event details
  to the Shell.

## Control Panel behavior

The Shell distinguishes unauthenticated responses, forbidden responses,
ordinary service errors, and unavailable dependencies:

- On unauthenticated responses, follow the documented sign-in flow and retain
  only a safe return path.
- On forbidden responses, show an access-denied state without redirecting
  repeatedly to sign-in.
- On unavailable services or timeouts, show a recoverable state and retry
  only under bounded guidance. A timeout is not proof that a write failed.
- On malformed or unexpected responses, fail closed for protected content,
  avoid rendering stale tenant-sensitive data, and report a safe diagnostic
  using `correlationId` when available.
- Show only safe API messages and details. Never expose secrets, tokens, or
  internal implementation information in UI, URLs, or client-side logs.

## Contract checklist

For every exposed endpoint, document:

- The stable error codes and their meaning, including validation,
  authentication, authorization, not-found, conflict, and dependency failures
  where applicable.
- The safe `message` and any allowed `details` shape for each code.
- HTTP status mapping and the behavior of the canonical envelope.
- Whether the error is caller-correctable, retryable, or potentially
  ambiguous for a write, and any required idempotency behavior.
- What correlation information is returned and how server-side diagnostics
  can be located without exposing them to the caller.
- The response behavior for asynchronous operations and provider failures.

The complete error catalog, exact status mappings, detailed validation
payloads, and error-code naming/versioning policy remain endpoint and Gateway
contract decisions; examples on this page do not establish those specifics.
