# Control Panel Responsibilities

## Purpose and boundary

The Control Panel Shell is the super administrator-facing web application for Daedalus. It
provides a consistent frame for operational and administrative views, gathers
user input, calls the API Gateway, and renders the responses. It is a
presentation component, not a domain service, data store, or security boundary.

The API Gateway is the Shell's only backend entry point. Domain services own
business rules and records; Auth owns authentication, identity, roles, and
permissions. The Gateway validates caller identity, and each target service
enforces tenant and resource authorization for its own operations.

## Responsibilities

The Shell is responsible for:

- Providing the shared application frame: layout, responsive navigation,
  breadcrumbs, page headings, and accessible interaction patterns.
- Presenting sign-in, signed-in, signed-out, loading, empty, unavailable, and
  error states using the documented Auth and Gateway contracts.
- Sending requests only to the API Gateway, attaching the caller's
  authentication context and a correlation ID as required by the contract.
- Composing user-facing views for customers, bookings, scheduling, jobs,
  payments, notifications, and administration where Gateway endpoints are
  defined.
- Managing transient presentation state, such as selected filters, open
  navigation, form input, and the currently displayed tenant context.
- Performing client-side input checks for usability and displaying validation
  feedback. These checks supplement, and never replace, server-side validation.
- Reflecting available views in navigation when supported by Gateway-provided
  identity or capability data. This is a presentation choice, not an access
  decision.
- Displaying asynchronous operation status from Gateway responses and
  refreshing it through Gateway-mediated requests.
- Keeping the UI usable and accessible across supported viewport sizes and
  input methods.

## Request and rendering flow

```text
User → Control Panel Shell → API Gateway → owning service → service-owned data
                           ← response envelope ←
```

1. The Shell collects a user action and performs any presentation-level
   validation.
2. It sends the request, authentication context, and correlation context to
   the appropriate Gateway route.
3. The Gateway validates the JWT and routes the request to the owning service.
4. The service validates the request and independently enforces tenant and
   resource authorization before reading or changing its data.
5. The Shell renders the returned view data or a safe, recoverable error state.

The Shell treats Gateway responses as its source for displayed domain state. It
does not infer that a request succeeded from a timeout, locally cached input,
or a client-side permission check. Asynchronous work is shown using the status
returned by the API.

## Data and state ownership

| Concern | Owner | Shell's role |
|---|---|---|
| Layout, routes, navigation, and transient view state | Control Panel Shell | Owns and renders |
| Authentication, users, roles, permissions, and identity | Auth | Presents Auth flows and identity data via the Gateway |
| Domain records and business rules | Owning domain service | Collects input and renders service-backed views |
| Tenant and resource authorization | Gateway and owning service | Displays context; does not make the enforcement decision |
| Persistence and domain events | Owning service and platform | Does not access storage or subscribe to events |
| Integration credentials and secret values | Owning service and Azure Key Vault | May present configuration flows; never reads or returns secret values |

Only transient presentation state belongs in the Shell. Business data is
persisted through Gateway operations and remains owned by the service
responsible for that domain. Any client cache must be treated as non-authoritative
and cleared or refreshed when identity or tenant context changes.

## Explicitly out of scope

The Shell must not:

- Implement or duplicate domain business rules, workflows, or authoritative
  validation.
- Connect to PostgreSQL, read or write service-owned tables, or hold database
  credentials.
- Call private services directly or bypass the API Gateway.
- Subscribe directly to Azure Service Bus or treat internal event payloads as
  a UI contract.
- Issue JWTs, manage roles or permissions, or make final authentication or
  authorization decisions.
- Treat a hidden navigation item, decoded token claim, or client-supplied
  `tenantId` as proof of access.
- Read Azure Key Vault or expose credentials, tokens, secret values, or
  sensitive internal payloads to browser code, URLs, logs, or telemetry.

## Boundary invariants

- All backend data access is mediated by the API Gateway.
- Tenant context is derived and validated by trusted backend components; a
  browser-provided tenant identifier alone is never trusted.
- Each domain service authorizes access to its own resources, even when the
  Gateway has already validated the JWT.
- The Shell renders only data returned through documented Gateway contracts
  and presents errors without leaking internal details or sensitive values.
- Correlation IDs are propagated where supported so requests can be diagnosed
  across the Gateway and services.
