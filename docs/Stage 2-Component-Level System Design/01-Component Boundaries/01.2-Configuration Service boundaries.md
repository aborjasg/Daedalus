# Configuration Service Boundaries

## Status and purpose

The current runtime-component, service-boundary, database, and Gateway
documents do not yet define a Configuration Service as a deployed service.
They specify neither a `configuration` PostgreSQL schema nor a
`/configuration/*` Gateway route. This page records the intended responsibility
boundary for configuration capabilities without treating those implementation
contracts as already established.

If Configuration is introduced as a service, its purpose is to own
configuration metadata that is shared across product modules or scoped to a
tenant. Configuration describes how a capability is set up; it does not own
the business records or execution of that capability. Until its service
contract is defined, configuration capabilities must be exposed through the
documented Gateway routes of their owning services.

## Intended ownership

The Configuration Service may own, once explicitly defined:

- Tenant-scoped configuration records for platform capabilities that do not
  belong to a single domain service.
- Configuration lifecycle metadata, such as enabled state, non-secret
  settings, validation status, and update timestamps.
- References to secrets stored in Azure Key Vault, together with
  non-sensitive provider metadata and rotation or connection status.
- Configuration-specific audit metadata, including actor, action, target, and
  correlation ID, without recording secret values.

Configuration is not an authority for identity, access control, or domain
behavior. Its records must not become a shared mutable data model for other
services.

## Ownership boundaries

| Concern | Owner | Configuration Service boundary |
|---|---|---|
| Users, tenant memberships, roles, permissions, and JWTs | Auth | Does not own or administer identity data |
| Customer, booking, scheduling, job, payment, and notification records and rules | Corresponding domain service | Does not persist or execute domain state |
| Shared or tenant-scoped non-secret capability settings | Configuration, if introduced | Owns only settings explicitly assigned to it |
| Integration secret values and credentials | Azure Key Vault, accessed by the owning service | Stores no secret values and does not give them to the Shell |
| Secret references and integration connection metadata | Service responsible for the integration; exact ownership must be specified per integration | Does not claim ownership of integration data without an explicit contract |
| Presentation state, forms, and configuration screens | Control Panel Shell | Renders and submits configuration through the Gateway; is not the system of record |
| Authentication and resource authorization | Gateway and the owning backend service | Does not treat a configuration record or UI permission as authorization |

The database model assigns PostgreSQL schemas to Auth and the named domain
services, but does not assign a schema to Configuration. If a Configuration
Service is approved, its schema and owned entities must be added to that model.
It must use service-owned persistence and must not read or write another
service's tables.

## API and interaction boundary

The Control Panel Shell calls the API Gateway only. Configuration operations,
if introduced, must be exposed through a documented Gateway route and
service-owned API contract. No route name, request/response schema, or
Configuration event is established by the current documentation; implementations
must not infer one from this page.

The expected interaction boundary is:

```text
Control Panel Shell → API Gateway → owning service → service-owned data
                                      ↕
                              Key Vault, for secrets
```

The owning backend service validates input, authenticates and authorizes the
caller in the trusted tenant context, applies configuration-specific rules,
and persists its own records. The Shell may perform usability checks and
display returned status, but it cannot make authorization decisions or treat
client-provided tenant identifiers as trusted.

Where a configuration operation changes behavior owned by a domain service,
that service remains responsible for validating and applying the change.
Cross-service communication must use documented APIs or versioned events;
direct table access and shared database models are not permitted. The current
documentation does not specify whether configuration changes are synchronous
or event-driven.

## Secrets and sensitive settings

- Store secret values, credentials, and signing keys in Azure Key Vault, not in
  PostgreSQL, browser state, configuration API responses, events, logs, or
  source control.
- Store only a Key Vault reference and approved non-sensitive metadata in
  service-owned persistence.
- Access Key Vault from the responsible backend using managed identity and
  least privilege. The Shell must never access Key Vault directly.
- Return only safe status and reference-safe identifiers to the Shell. Never
  return the secret value, even to an authorized configuration administrator.
- Redact secrets and sensitive payloads from diagnostics and audit records.

For integrations, the system flow assigns writing credentials to the owning
service and requires it to return status without secret material. A shared
Configuration Service must not supersede that ownership unless an integration
contract explicitly assigns it responsibility.

## Authorization, tenancy, and audit

Auth remains the authority for identity, roles, and permissions. The Gateway
validates the JWT, and the service handling a configuration request enforces
tenant and resource authorization for its own records. A valid token, a visible
configuration page, or a client-held tenant identifier is not sufficient
authorization.

Tenant-scoped configuration must be isolated by trusted tenant context and
service-side authorization. Administrative changes should be auditable with
the actor, tenant, target, action, outcome, and `correlationId`, without
including credentials or secret values. The exact permission names, audit
storage, retention policy, and configuration-specific roles remain to be
defined by the corresponding contracts.

## Contract gaps before implementation [TODO]

The following decisions are not settled by the current `/docs` architecture
contracts and must be documented before a standalone service is implemented:

- Whether Configuration is a separate runtime service or configuration remains
  owned by existing domain services.
- Which configuration entities are owned by Configuration and which remain
  with Auth, domain services, or integration owners.
- The PostgreSQL schema, data model, tenant-scoping rules, and concurrency
  behavior, if a Configuration schema is introduced.
- Gateway route names, API request/response schemas, validation errors, and
  versioning.
- Whether updates are applied synchronously or published as events, and any
  event schema, delivery, retry, and idempotency requirements.
- Configuration-specific permissions, audit requirements, and ownership for
  each integration's Key Vault references and metadata.
