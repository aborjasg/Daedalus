# Integration Service Boundaries

## Status and purpose

The canonical runtime-component, service-boundary, and database documents do
not currently define a standalone Integration Service, an `integrations`
PostgreSQL schema, or an `/integrations/*` Gateway route. They assign
integration work to the service that owns the related capability. This page
defines those current boundaries and records the decisions needed if a
standalone Integration Service is later introduced.

An integration connects a Daedalus capability to an external provider or
consumer. Integration code adapts protocols and payloads; it does not transfer
ownership of the business process or records to the external system or to a
shared integration component.

## Current ownership model

Each domain service owns and operates integrations needed to fulfill its own
responsibilities. The service validates provider-specific data, applies
domain rules, persists its own state, and handles provider outcomes. Examples
in the current architecture include Payments resolving payment-provider
credentials and Notifications delivering messages through its channels.

| Concern | Owner | Boundary |
|---|---|---|
| Payment-provider requests, payment intents, transactions, refunds, and reconciliation | Payments | Owns payment workflows and provider references; does not own customer master data or booking state |
| Notification-provider delivery, templates, attempts, and delivery status | Notifications | Owns message delivery and status; does not own the domain records that trigger messages |
| Other provider behavior | Service that owns the capability | Adapter and provider state remain within that service's business and data boundary |
| Public inbound API access | API Gateway and target service | Gateway is the external entry point; the target service authenticates context and authorizes its own resources |
| Provider credentials and secret values | Azure Key Vault, accessed by the owning service | Values are never stored in PostgreSQL or returned to the Shell |
| Secret references and non-secret provider metadata | Owning service | Persist only in that service's schema; no cross-service table access |
| User-facing integration setup and status views | Control Panel Shell | Calls documented Gateway APIs and renders safe results; it is not an integration runtime |
| Identity, roles, and permissions | Auth | Does not own provider connections or domain authorization decisions |

The word “integration” does not imply that a shared service owns all provider
connections. A provider adapter must not read or write another service's
schema. If information is needed across service boundaries, use documented
APIs or versioned events; any cached external facts are non-authoritative.

## Request and data flows

### Inbound requests

External clients, including provider callbacks where supported, enter through
the API Gateway. The Gateway validates the applicable authentication and
request policy, then routes to the service that owns the target capability.
That service validates the payload, verifies provider-specific authenticity
where applicable, enforces tenant and resource rules, and changes only its own
data. The current documentation does not define callback routes or callback
authentication schemes; these must be specified by the owning API contract.

### Outbound provider calls and credential setup

```text
Control Panel Shell → API Gateway → owning service → external provider
                                          ↕
                                      Key Vault
```

For connection setup, an authorized tenant administrator submits credentials
through the Gateway to the owning service. That service writes secret values
to Key Vault, persists only the Key Vault reference and approved non-secret
metadata in its own schema, and returns connection status without secret
material. For runtime provider calls, the same owning service resolves the
secret through its managed identity and least-privilege Key Vault access.

Rotation updates the Key Vault value and the owning service's associated
metadata. Disconnect revokes or deletes the provider credential according to
provider policy, removes or disables its reference and metadata as appropriate,
and records a safe outcome. The detailed lifecycle, retention, and failure
behavior are provider-specific contracts and are not established here.

## Security and tenant isolation

- Auth remains the authority for user identity, roles, and permissions. The
  Gateway validates the caller's JWT; the owning service independently enforces
  tenant and resource authorization.
- Derive tenant context from trusted backend identity context, not an
  arbitrary request-body field. Tenant-scoped persistence uses `tenant_id`;
  API and event contracts use `tenantId`.
- Give each service least-privilege access to its own data and the Key Vault
  secrets it needs. Do not share provider credentials between tenants or
  services unless a separately reviewed contract requires it.
- Never expose secret values, access tokens, or sensitive provider payloads in
  Shell responses, URLs, events, logs, or source control. Return only
  reference-safe identifiers and safe status.
- Redact sensitive fields from diagnostics. Propagate `correlationId` through
  Gateway requests and service operations without using it as a substitute
  for authorization.

The Shell may show or hide setup screens based on Gateway-provided identity or
capability information, but that presentation does not authorize a connection
change. Direct requests receive the same backend authorization checks.

## Reliability and operational boundaries

The owning service is responsible for provider timeouts, bounded retries,
idempotency where operations may be repeated, and reconciliation of uncertain
outcomes. Do not retry a non-idempotent provider operation unless the provider
contract supports safe deduplication or the service can establish its outcome.

When an operation must publish a domain event, the owning service publishes
after durable persistence using the documented outbox/inbox and Service Bus
reliability patterns. Consumers are idempotent; transient failures use bounded
retry, and poison messages are dead-lettered and alerted. The Gateway does not
publish domain events on behalf of services. Provider-specific event schemas
and callback delivery guarantees remain to be documented.

Record operational status and errors without secret material. Use structured
logs, metrics, traces, and correlation IDs to observe connection failures,
provider latency, retries, and delivery outcomes through Azure
Monitor/Application Insights.

## Standalone Integration Service: decision required

If a centralized Integration Service is proposed, it must have an explicit
runtime and data boundary before implementation. In particular, decide:

- Whether it is only a shared adapter/connection-management capability or is
  intended to own any business workflows. Domain services must remain owners
  of their records and authorization decisions.
- Which provider connections and metadata it owns, and how domain services
  invoke it through APIs or versioned events rather than shared tables.
- Its database schema and ownership of Key Vault references, if any.
- Its Gateway routes, authentication model for inbound callbacks, API
  schemas, error behavior, and versioning.
- Credential provisioning, rotation, revocation, tenant isolation, least
  privilege, and audit requirements.
- Provider-specific timeouts, idempotency, retries, reconciliation, event
  contracts, and operational service-level objectives.

Until those decisions are documented, do not assume a standalone service,
shared `integrations` schema, direct Shell-to-provider access, or generic
integration endpoint. Use the documented Gateway route and owning service for
each capability.
