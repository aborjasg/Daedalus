# Data Model: Billing Model

## Purpose and status

Billing describes the commercial relationship and charges associated with
using Daedalus or with transactions processed for a tenant's own customers.
These are separate domains and must not be conflated:

- **Platform billing** is a possible Daedalus-to-tenant subscription or
  usage-billing capability.
- **Customer payments** are payment workflows a tenant operates for its own
  customers.

The current database model assigns the `payments` schema to payment intents,
transactions, refunds, reconciliation, and provider references. It does not
define platform plans, tenant subscriptions, invoices, billing accounts,
usage meters, entitlements, or a billing service. The logical concepts below
do not establish their implementation, owner, physical schema, or API
contract. In particular, the existence of Payments does not imply that it
owns SaaS subscription billing.

## Domain boundaries

| Concern | Current or proposed owner | Boundary |
|---|---|---|
| Customer-facing payment intents, transactions, refunds, reconciliation, and provider references | Payments | Established in the database model; serves product payment workflows and does not imply platform subscription billing |
| Payment-provider connection and credentials | Payments, with secret values in Azure Key Vault | Payments owns provider behavior and references; Key Vault stores secret values |
| Platform plans, subscriptions, invoices, and billing accounts | Not assigned by current docs | Must be assigned to a service and documented before implementation |
| Usage measurement and aggregation | Not assigned by current docs | Requires an explicit source of truth, ownership, and event/retention contract |
| Feature and module availability or entitlements | Not assigned by current docs | Must not be inferred from a plan or subscription until an authoritative contract exists |
| Identity, tenant membership, roles, and permissions | Auth | Billing status does not grant identity or permissions |
| User-facing billing screens | Control Panel Shell | Presentation only; calls documented Gateway APIs and is not the system of record |

No service reads or writes another service's tables. Cross-service references
use opaque identifiers, and current data is obtained through documented APIs
or events rather than cross-schema joins.

## Logical platform-billing concepts

If Daedalus platform billing is introduced, an owning service may need logical
records for:

| Concept | Purpose | Status |
|---|---|---|
| Billing account | Associates a tenant with a platform billing relationship and safe billing metadata. | Not defined in the current data model. |
| Plan or price definition | Describes a commercial offer, price, currency, and applicable billing terms. | Plans and pricing are not defined by current docs. |
| Subscription | Represents a tenant's enrollment in a plan over a documented lifecycle. | Tenant subscriptions are not defined by current docs. |
| Invoice or statement | Records amounts owed or charged for a billing period and its settlement state. | Platform invoices are not defined by current docs. |
| Usage record or aggregate | Represents metered consumption used in a billing calculation, if usage billing is supported. | Usage metering and its source of truth are not defined by current docs. |
| Entitlement | Represents an explicit capability allowance derived from an authoritative commercial policy. | Entitlement ownership and evaluation are not defined by current docs. |
| Billing event/audit record | Captures safe lifecycle changes, adjustments, and provider outcomes. | Exact event and audit contracts are not defined by current docs. |

These are logical concepts, not approved table names or required entities.
Do not create them until the business model, owner, and contracts are
approved. In particular, do not assume that every tenant has one subscription,
that plans are mutable, that an invoice is paid synchronously, or that
entitlements are equivalent to module assignments.

## Logical relationships

```text
Tenant
  └── Platform billing account (optional; ownership not assigned)
        ├── Subscription ──> Plan/price definition
        ├── Invoice/statement
        ├── Usage record or aggregate (optional)
        └── Provider reference and safe billing status

Tenant
  └── Customer payment workflows (Payments-owned)
        ├── Payment intent
        ├── Transaction
        ├── Refund
        └── Reconciliation
```

The platform-billing branch and customer-payment branch may use external
payment providers, but that does not make them the same business record or
authorize shared persistence. Any provider reuse must be explicitly designed
with separate ownership, tenant scoping, credentials, reconciliation, and
audit requirements.

## Tenant scope and data invariants

- Tenant-scoped billing records use `tenant_id` in PostgreSQL; API and event
  contracts use `tenantId`.
- The Gateway establishes trusted tenant context from the validated
  identity. A client-supplied tenant identifier is not authoritative. The
  owning service independently authorizes each billing operation and
  resource.
- Reads, writes, aggregates, exports, and background processing are scoped
  to the trusted tenant context. Resource identifiers alone do not authorize
  access or reveal another tenant's billing records.
- If a platform-level record is intentionally not tenant-scoped, its owner
  must document its visibility, access rules, and relationship to tenants.
  Missing `tenant_id` is not by itself evidence that a record is global.
- Tenant-local uniqueness and relationships must be enforced by the owning
  service's schema and constraints. Cross-service references remain opaque
  identifiers, not foreign keys or cross-schema joins.
- Administrative or system-wide billing operations require explicit
  authorization, a documented scope, and audit records. They must not use a
  missing tenant context as a broad-access fallback.
- Billing data may contain financial or personal information. The owner must
  define data minimization, retention, export, deletion, and audit policies
  before implementation; current docs do not define billing-specific
  retention or regulatory requirements.

## Money, status, and lifecycle

Current documentation does not define currency, amount precision, tax,
rounding, billing periods, proration, invoice numbering, payment terms, or
accounting rules. Those are domain decisions and must be specified by the
owner before defining DTOs or storage. Do not represent monetary values using
an undocumented floating-point format or infer a currency from tenant
location.

The owner must define lifecycle states and allowed transitions for any
subscription, invoice, payment, refund, or usage record. Payment-provider
status and a billing business status are not necessarily the same state.
Provider callbacks and asynchronous outcomes must be authenticated,
validated, idempotently processed where supported, and reconciled by the
responsible service. Exact state names, transition rules, and retry behavior
are not established by the current docs.

## Provider data and secrets

For documented Payments workflows, the owning service stores provider
references, approved non-secret metadata, status, and rotation timestamps in
its own schema. Secret values and credentials are stored in Azure Key Vault,
not in PostgreSQL, browser state, API responses, events, logs, or source
control. The responsible backend uses managed identity and least-privilege
access.

If platform billing uses a provider, its credential and provider-reference
ownership must be explicitly assigned. Do not presume the existing Payments
provider connection belongs to platform billing or may be shared across
tenants or workflows. External provider identifiers are not substitutes for
Daedalus authorization checks.

## API, events, and operational behavior

The API Gateway is the public entry point. Billing routes, endpoint-specific
DTOs, error codes, idempotency scopes, and HTTP status mappings are not
defined by current docs. Each operation must be specified by its owning
service contract. Responses expose only data the caller is authorized to
receive and must not include credentials, secret values, internal provider
payloads, or another tenant's billing details.

Where services publish billing-related domain events, they publish after
durable persistence using documented, versioned event schemas. Consumers
validate the tenant context, handle duplicates safely, and do not use event
payloads to bypass service ownership. The current docs do not define billing
event names, delivery guarantees, or usage-metering semantics.

Operations must account for provider timeouts, bounded retries,
idempotency, uncertain outcomes, and reconciliation as applicable. Log safe
outcomes and propagate `correlationId`; redact tokens, credentials, and
sensitive payment data. Do not claim a charge, refund, invoice settlement,
or subscription change succeeded until the owning workflow has established
its outcome.

## Entitlements and feature availability

The current docs explicitly leave module availability and plan restrictions
unassigned. If commercial entitlements are introduced, define an authoritative
owner and an explicit contract between billing and the capability that
enforces the entitlement. Do not infer access from a plan label, invoice
status, payment success, feature toggle, or UI visibility alone.

Entitlements, if adopted, remain distinct from:

- Auth roles and permissions, which govern who may act.
- Module availability, which governs which product module is offered.
- Feature toggles, which control capability behavior or rollout.
- Module settings, which configure an available capability.

The owning backend service must enforce the applicable entitlement and its
own tenant/resource authorization for direct API requests. Shell visibility
and client-side checks are not security controls.

## Decisions before implementation

Before implementing platform billing or extending Payments to support it,
document:

- Whether the requirement is customer payment processing, Daedalus platform
  subscription billing, usage billing, or a combination, and define the
  boundary between them.
- The owning service and source of truth for billing accounts, plans/prices,
  subscriptions, invoices, usage, provider connections, and entitlements.
- The business model: supported currencies, amount precision, taxes,
  billing periods, proration, adjustments, refunds, and settlement semantics
  as applicable.
- The physical schema, identifiers, tenant scope, uniqueness, concurrency,
  lifecycle, retention, and audit requirements.
- Provider selection, credential ownership, Key Vault access, callbacks,
  reconciliation, idempotency, and failure recovery.
- Gateway routes, DTOs, error behavior, permissions, API versioning, and
  safe disclosure rules.
- Event contracts and usage-metering sources, delivery, deduplication,
  correction, and retention behavior if asynchronous processing is used.
- Whether and how billing affects module availability or entitlements,
  including the authoritative policy and enforcement point.

Until those decisions are documented, treat platform billing entities as
proposals only. Continue to keep the documented Payments domain focused on
payment intents, transactions, refunds, reconciliation, and provider
references; do not infer a subscription schema, billing service, or
plan-based authorization from the current `/docs` architecture.
