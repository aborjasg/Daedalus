# Data Model: Module Settings

## Purpose and status

Module settings are non-secret configuration values used to tailor a module's
behavior for an approved scope, such as a tenant. They are distinct from
module availability, Auth permissions, integration connection metadata, and
domain records.

The current authoritative database and service-boundary documents do not
define a `module_settings` table, its PostgreSQL schema, or a service that
owns all module settings. Older Control Panel notes mention the table, but
also describe direct Shell access to data; that conflicts with the current
architecture, where the Shell is presentation-only and services own their
data. This page therefore describes a logical model, not an approved
physical schema or API.

Until ownership is assigned, settings must remain with the service that owns
the behavior they configure. A standalone Configuration Service may own only
settings explicitly assigned to it through an approved service boundary and
contract.

## Logical entities

| Entity | Purpose | Ownership |
|---|---|---|
| Setting definition | Describes a supported setting, its module, type, validation constraints, default behavior, and whether it may be changed at a given scope. | The service that owns the setting's behavior; a shared catalog owner is not currently specified. |
| Scoped setting value | Holds an approved non-secret override for a setting at its documented scope. | Service responsible for the configured behavior, unless ownership is explicitly transferred. |
| Setting change audit | Records who changed which setting, for which tenant and target, with outcome and `correlationId`. | Responsible service and its established audit mechanism. |

These are logical concepts, not prescribed table names. A service may represent
definitions and values differently when its contract preserves the ownership,
validation, tenant-isolation, and security rules below.

## Logical relationships

```text
Module (stable identifier)
  └── Setting definition
        ├── allowed scope and value type
        ├── validation/default behavior
        └── scoped setting value (optional override)
              └── tenant, when tenant-scoped

Auth identity and permissions ──authorize change/read──> owning service
Integration credential ──not a module setting──> Azure Key Vault
```

A setting may refer to a module by stable opaque identifier. That reference
does not grant access to the module catalog or transfer ownership of the
setting. The Module model describes catalog and availability decisions
separately; module settings must not be used to enable modules or implement
plan restrictions unless those responsibilities are explicitly assigned.

## Scope and precedence

The current documentation does not define a universal setting scope or
inheritance model. Each setting's owning contract must explicitly state
whether it is:

- A service-wide default, not tenant-editable.
- A tenant-specific override.
- A user-specific presentation preference, if the relevant owner and storage
  boundary are defined.

Do not assume organization, environment, user, or module scopes are
interchangeable. If defaults and overrides are supported, define precedence,
fallback, reset, and behavior when a value is absent. Resolve effective values
within the owning service; do not make the Shell infer policy from a
combination of client caches.

## Logical attributes and invariants

The owning service defines concrete columns and API DTOs. A setting definition
and value should express, as applicable:

- Stable setting identifier and associated module identifier.
- A value type and documented serialization format.
- Allowed scope, mutability, and whether a default exists.
- Validation constraints, allowed values, and safe user-facing description.
- Non-secret configured value or an explicit representation that the value is
  unset and the service default applies.
- For tenant-scoped values, a trusted tenant association persisted as
  `tenant_id`.
- Update metadata and optimistic concurrency/version information where the
  owning schema requires it.

Do not store redundant or derived values if the owning service can safely
derive them from its authoritative state. Do not persist arbitrary keys or
unvalidated JSON that could bypass the setting definition's type and
constraints. Unknown-key and unknown-field behavior must be specified by the
service contract.

Names, table layout, uniqueness constraints, schema migrations, maximum
value sizes, and concurrency strategy are not defined by current docs. The
owning service must decide and document them before creating persistence.

## Ownership and data boundaries

- The service responsible for a behavior owns and validates settings that
  change that behavior. Configuration storage does not move ownership of the
  domain process or records.
- The Shell owns only transient form and view state. It submits changes through
  the API Gateway and renders the owning service's response; it does not read
  or write PostgreSQL tables.
- Auth owns identity, roles, and permissions. The Gateway validates the JWT,
  and the service handling a setting operation enforces tenant and resource
  authorization.
- Services do not read or write another service's tables. Cross-service
  references use opaque IDs and documented APIs or versioned events, not
  shared mutable models or cross-schema joins.
- Module settings do not include module catalog records, tenant module
  availability, integration connection state, usage metrics, or domain
  entities unless an explicit contract assigns that data.

The named PostgreSQL schemas in the current database model are
`auth`, `customers`, `bookings`, `scheduling`, `jobs`, `payments`, and
`notifications`. It does not assign a `configuration` schema or a
module-settings schema. Any new schema and its data owner must be added to
the authoritative database and service-boundary documentation.

## Security and sensitive values

- Store only values approved for the setting's type and scope. Treat tenant
  settings as tenant-scoped data and isolate them using trusted tenant
  context.
- Never trust a client-supplied `tenantId` as the source of authorization.
  API/event contracts use `tenantId`; PostgreSQL uses `tenant_id`.
- Do not store passwords, access tokens, signing keys, credentials, or other
  secrets as module setting values. Store secret values in Azure Key Vault;
  persist only a Key Vault reference and approved non-sensitive metadata in
  the responsible service.
- Do not return secret values in API responses or expose them in Shell state,
  URLs, logs, events, audit records, or source control.
- Validate reads and writes server-side. A visible settings page, module
  assignment, role claim, or valid JWT alone does not authorize a change or
  access to every tenant/resource.
- Audit administrative changes with actor, tenant, setting identifier,
  target, outcome, and `correlationId`, while redacting secret and sensitive
  values.

## API and change behavior

The Shell uses documented `/api/v1` Gateway routes and the common response
envelope. The current documentation defines no generic module-settings
endpoint or request/response schema. The owning service must document the
HTTP method and route, setting identifiers, scope, validation, concurrency
behavior, errors, and authorization before clients depend on them.

Successful update responses should let the caller distinguish the accepted
setting state from validation failures without exposing internal storage.
If an update is asynchronous, return the documented operation/status DTO and
let the Shell refresh status through the Gateway. Do not treat a timeout as
proof that a write failed; define idempotency and retry behavior for operations
that may be safely repeated.

If changes must affect another service, the owning service communicates
through a documented API or versioned event after durable persistence. The
Gateway does not publish domain events on behalf of a service. Current docs do
not prescribe whether setting changes are synchronous, event-driven, or
cached by consumers.

## Decisions before physical implementation

Document these decisions before implementing a shared or persisted
module-settings model:

- Owner and source of truth for each setting and any shared setting catalog.
- Supported scopes, defaults, inheritance, reset behavior, and mutability.
- Physical schema, identifiers, constraints, validation, concurrency, and
  migration strategy within the owning service.
- Which settings are sensitive and how secret references are handled.
- Gateway routes, request/response DTOs, errors, authorization, and
  idempotency/retry semantics.
- Whether changes affect other services, and any event/API contract, consumer
  behavior, and cache invalidation requirements.
- Audit fields, access policy, retention, and operational diagnostics.

Until those decisions are recorded, treat module settings as service-owned
configuration concepts. Do not assume a central `module_settings` table,
direct Shell database access, or a standalone Configuration Service.
