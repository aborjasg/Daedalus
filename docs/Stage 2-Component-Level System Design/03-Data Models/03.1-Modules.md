# Data Model: Modules

## Purpose and status

A module is a product-facing capability grouping in the Control Panel, such as
Customers, Bookings, Scheduling, Jobs, Payments, or Notifications. It provides
a stable way to organize navigation, pages, and module-scoped permissions.
A module is not necessarily a deployable service: backend services own domain
behavior and data, while the Control Panel Shell provides the presentation
frame.

The current authoritative database model does not define a `modules` table, a
`tenant_modules` table, or a module-owning PostgreSQL schema. Earlier Shell
notes refer to those names, but the current architecture assigns no owner or
schema to them. The entities below therefore describe the logical model and
proposed relationships; they are not an approved physical schema or API
contract.

## Logical entities

| Entity | Purpose | Ownership boundary |
|---|---|---|
| Module catalog entry | Describes a product capability available to the application, with a stable key and presentation metadata. | Catalog ownership and storage location are not assigned by the current service-boundary docs. |
| Tenant module assignment | Records whether a tenant has a capability available, if product provisioning or plan policy requires tenant-level enablement. | Must be assigned to an owning service before persistence is implemented. |
| Module permission | Names an action or access capability within a module. | Auth owns roles and permissions; permission definitions and assignments remain in Auth's boundary. |
| Module settings | Holds configuration for a module, if settings are needed. | Settings ownership must follow the configuration boundaries in [03.3-Module-Settings.md](./03.3-Module-Settings.md); module availability is not itself settings data. |

## Logical relationships

```text
Module catalog entry
    ├── Tenant module assignment (optional, tenant-scoped)
    └── Module permission definitions (Auth-owned)
            └── Role-to-permission assignments (Auth-owned)

Tenant membership ──evaluated with──> module permissions
Tenant plan/subscription ──may constrain──> tenant module availability
```

The relationship to tenant plans or subscriptions is conditional. Although
older Shell notes mention plan restrictions, the current authoritative data
model does not define plan or subscription entities. Do not make module
availability depend on billing data until its owner and contract are defined.

## Logical attributes and invariants

If the catalog and assignment entities are adopted, define their concrete
columns and API DTOs in the owning service contract. At minimum, preserve
these logical properties:

- A module has a stable, machine-readable identifier that is independent of
  its display name, navigation label, or route.
- Presentation metadata (such as display name, description, icon, and
  navigation grouping) is not authorization policy.
- A tenant assignment, if used, identifies both the tenant and module and has
  an explicit availability state. Its lifecycle and allowed states must be
  documented by its owner.
- Permission definitions identify a module and an action, but remain part of
  Auth's permission model. Role assignments are evaluated in the user's
  tenant context.
- Tenant-scoped records use `tenant_id` in PostgreSQL. Tenant context is
  derived from trusted backend identity context, never from an unchecked
  request field.
- Cross-service relationships use stable opaque identifiers. Services do not
  join against another service's tables or treat a UI catalog as authoritative
  domain data.
- Module settings and integration connection metadata are separate concerns;
  do not embed their mutable state or secret values in catalog entries.

Proposed uniqueness constraints, identifier format, deletion behavior,
versioning, and catalog lifecycle are not specified in current docs and must
be decided by the owning service. If tenant assignments are persisted, their
owner should define how duplicate assignments and concurrent updates are
prevented.

## Availability and authorization

Module availability and permission are distinct checks:

1. The product may determine that a module is available to a tenant, if a
   tenant assignment or plan policy is defined.
2. Auth provides identity, tenant membership, roles, and module-scoped
   permissions.
3. The Shell may use Gateway-provided identity or capability information to
   shape navigation and visible views.
4. The API Gateway validates the caller's JWT and applies coarse policy.
5. The service that owns the requested resource independently enforces
   tenant and resource authorization.

A visible module, enabled tenant assignment, role, or valid JWT alone does
not grant access to every resource. Hidden navigation and client-side checks
are presentation behavior, not security controls. Direct URLs and API
requests receive the same backend authorization checks.

## Service and data boundaries

- The Control Panel Shell owns module presentation, navigation, routing, and
  transient view state. It does not directly read module or tenant tables.
- Auth owns users, tenant memberships, roles, permissions, and role
  assignments. It does not own customer, booking, job, payment, or
  notification records.
- Each domain service owns its domain records and enforces access to its own
  resources.
- No service reads or writes another service's tables. Cross-service module
  metadata, if required, is provided through documented APIs or versioned
  events.
- The current docs do not assign module catalog, tenant enablement, plan
  restrictions, or usage metrics to a runtime service or schema. Do not
  implement direct Shell database access or assume a shared module database
  until those ownership decisions are documented.

## Contract decisions before physical schema

Before implementing module persistence or APIs, document:

- The owner and source of truth for the module catalog and tenant module
  availability.
- Whether modules are solely navigation groupings or carry additional
  lifecycle and provisioning behavior.
- The physical schema, stable identifiers, tenant scoping, uniqueness,
  concurrency, and lifecycle rules.
- Whether plan or subscription policy affects availability, and which service
  owns that policy and its data.
- How Auth defines module-scoped permissions and how services receive trusted
  authorization context.
- The API or event contract by which the Shell and services discover module
  availability, including failure and cache-refresh behavior.
- How this model relates to module settings, integrations, audit records, and
  usage metrics without transferring their ownership.
