# Data Model: Feature Toggle Model

## Purpose and status

Feature toggles control whether a defined product capability is available in
a given context, allowing capabilities to be enabled or disabled without
changing the deployed code. They may support controlled rollout, operational
kill switches, or temporary development of a capability.

The current `/docs` architecture does not define a Feature Toggle Service,
feature-toggle PostgreSQL schema or tables, evaluation API, event contract, or
toggle-administration routes. This page defines a logical model and its
boundaries; it does not establish a physical schema or assign ownership to a
runtime service. The model must be assigned to an owner before implementation.

## Scope and distinctions

A feature toggle is a runtime decision about whether a capability's behavior
is enabled. It is distinct from:

- **Module availability:** whether a product module is offered to a tenant.
  The module catalog and tenant enablement ownership are not assigned by the
  current docs; see [03.1-Modules.md](./03.1-Modules.md).
- **Module settings:** configuration values that customize an available
  capability; see [03.3-Module-Settings.md](./03.3-Module-Settings.md).
- **Authorization:** whether an identified actor may perform an operation.
  Auth owns roles and permissions, and the service that owns a resource
  enforces tenant and resource authorization.

An enabled toggle is never, by itself, authorization to access data or invoke
an operation. A disabled toggle is not a replacement for authorization,
validation, or secure handling of the underlying capability.

## Logical entities

| Entity | Purpose | Ownership boundary |
|---|---|---|
| Feature definition | Stable key and description of a toggleable capability, including its intended purpose and lifecycle category. | Catalog ownership is not assigned by current service-boundary docs. |
| Toggle rule | Represents the enabled state and any supported scope or targeting conditions for a feature. | Must have an explicitly assigned owner and source of truth before persistence. |
| Evaluation context | Trusted attributes used to evaluate a toggle, such as environment and, where allowed, tenant context. | Established by the trusted backend caller; client-provided attributes are not authoritative. |
| Evaluation result | The effective decision for a feature in a particular context, with any documented reason or safe metadata. | Produced by the designated evaluator; must not disclose another tenant's rule or context. |
| Toggle change audit record | Records who changed a rule, what changed, when, and the outcome. | Must use the responsible service's established audit mechanism. |

These are logical concepts, not approved table names or API DTOs. A feature
definition and its rules may be stored together or separately by the eventual
owner. Do not create shared toggle tables or a central service solely because
multiple domain services need feature decisions.

## Logical relationships

```text
Feature definition
  └── Toggle rule(s), if multiple scopes or rollout stages are supported
        ├── environment scope
        ├── tenant scope (optional, tenant-scoped)
        └── other documented targeting attributes (optional)

Trusted evaluation context
  └── Feature decision

Authorized toggle change
  └── Audit record
```

The scope hierarchy, if any, must be explicit. A global default, environment
override, tenant override, or actor-specific rule must not be assumed until
the owner documents the precedence and conflict behavior. Avoid targeting
based on untrusted request fields or sensitive attributes that are not
necessary for the capability.

## Logical attributes and invariants

If the model is adopted, the owning contract should define at least:

- A stable, machine-readable feature key, independent of display name, route,
  deployment name, or UI label.
- A concise description, owning team or service, purpose, and lifecycle
  category (for example, temporary rollout or operational control).
- The rule's enabled state, supported scope, effective time window if
  applicable, and documented precedence when multiple rules match.
- Optional rollout or targeting configuration, constrained to explicitly
  supported attributes and validated by the owner.
- Creation and update metadata, concurrency behavior, and an audit trail for
  administrative changes.
- A retirement state or removal process so temporary toggles are not left
  indefinitely without an owner.

Concrete field names, value types, allowed targeting expressions, identifier
format, storage constraints, and lifecycle states are not established by
current docs and must be specified by the owner. Feature keys must not be
reused for a different capability after retirement.

## Evaluation and service boundaries

- Evaluate toggles on the server for operations that affect protected data,
  business behavior, or security boundaries. Client-side evaluation may
  shape presentation but is not authoritative.
- The caller establishes evaluation context from trusted identity and
  deployment information. A tenant-scoped evaluation uses trusted
  `tenantId` context; PostgreSQL uses `tenant_id`. A supplied tenant value
  must not override context established by the Gateway and validated by the
  owning service.
- Each service remains responsible for authorization and domain invariants
  when it evaluates or consumes a toggle decision. Do not let a shared
  evaluator become a source of authorization policy or permission data.
- Services must not read or write another service's toggle tables. If toggle
  evaluation is centralized, it must be accessed through a documented API or
  versioned event contract; if evaluation is local, ownership and
  synchronization must be defined.
- Toggle rules and results must be isolated by their documented scope. Tenant
  A's override or evaluation must not affect tenant B. Tenant-scoped toggle
  records, if persisted, use `tenant_id` and follow the trusted tenant
  isolation rules.
- Responses to the Shell or other clients expose only the decisions and safe
  metadata they need. They do not expose private rollout rules, other
  tenants' configuration, internal targeting attributes, or audit details.

The current docs do not establish whether evaluation is synchronous,
cached, or event-driven, nor do they define cache invalidation or consistency
requirements. Those behaviors must be specified by the toggle owner and
consuming services before integration.

## Failure behavior and safety

The owner must document the behavior when a toggle cannot be evaluated,
including unavailable storage, stale cached data, invalid rules, and missing
context. Do not silently substitute an enabled state or a broad/default
tenant. The fallback must be selected per capability and must preserve
security and data integrity; security-sensitive checks remain enforced
independently of toggle evaluation.

Toggle checks should not create partial or inconsistent writes. Where a
toggle gates a mutation or workflow, the owning service evaluates it at the
appropriate point in the operation and documents how retries and concurrent
rule changes behave. Exact consistency, timeout, and retry requirements are
not specified by current docs.

## Administration, audit, and operations

Toggle changes are configuration changes, not ordinary end-user requests.
The owner must define which authenticated administrative roles can create,
modify, enable, disable, or retire toggles. Auth remains authoritative for
identity and permissions; the service responsible for the toggle change
enforces authorization in the trusted tenant context where applicable.

Record auditable changes with actor, applicable tenant, feature key, previous
and new safe state, action, outcome, timestamp, and `correlationId` where
available. Do not log tokens, credentials, secret values, or unnecessary
sensitive targeting data. Operational kill switches should have a documented
owner, intended effect, and safe recovery procedure.

## Relationship to modules, settings, and billing

- A module can be available while one of its features is disabled, and a
  feature toggle can gate behavior without hiding the whole module.
- Module visibility in the Shell is presentation behavior. The backend must
  enforce the applicable toggle and authorization checks for direct API
  requests as well.
- Module settings configure behavior; they must not be used as an
  undocumented substitute for a feature-toggle rule.
- Current docs do not define billing plans or subscriptions as authoritative
  entities. Do not infer feature entitlements from an undocumented plan,
  subscription, or tenant-module relationship.
- Toggle evaluation does not provision resources, migrate data, or replace a
  service's documented domain lifecycle.

## Contract decisions before implementation

Before introducing toggle persistence, evaluation, or administration, document:

- The service and team that own the feature catalog, rules, evaluation, and
  audit records, including whether there is a dedicated service.
- Whether toggles are global, environment-scoped, tenant-scoped, or support
  additional targeting, and the precedence when scopes overlap.
- The trusted evaluation context and its propagation through Gateway,
  backend services, and asynchronous consumers.
- The storage model, tenant scoping, indexes, uniqueness, concurrency, and
  lifecycle/retirement rules.
- API routes, request and response DTOs, error behavior, authorization
  permissions, and versioning for administration and evaluation.
- Evaluation consistency, caching, invalidation, timeout, retry, and failure
  behavior.
- Which capabilities may use toggles, the safe fallback for each category,
  and how security and authorization remain independent.
- Audit content, retention, operational ownership, and cleanup expectations
  for temporary toggles.

Until these contracts exist, treat feature toggles as a logical design only:
do not assume an owning schema or service, expose client-controlled tenant
targeting, or use a toggle as an authorization or module-entitlement check.
