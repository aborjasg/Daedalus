# Data Model: Multi-tenant Isolation

## Purpose and status

Daedalus hosts data for multiple tenants. Tenant isolation is a cross-cutting
data-access invariant: a user, service account, or operation acting in one
tenant context must not read or change another tenant's data unless an
explicitly authorized and documented cross-tenant workflow exists.

The current database model assigns service-owned PostgreSQL schemas for Auth
and each domain service. Tenant-scoped tables use `tenant_id` in PostgreSQL;
API and event contracts use `tenantId`. PostgreSQL Flexible Server may host
these schemas initially; separate databases per service are not required.
This document specifies logical isolation rules, not a complete physical
schema, PostgreSQL row-level security policy, or endpoint contract.

## Tenant identity and trusted context

- Auth owns tenants' user memberships, roles, and permissions. A user may
  belong to more than one tenant; authorization is evaluated in the active
  tenant context, not from a global role alone.
- The API Gateway validates the Auth-issued JWT and establishes trusted
  `tenantId` context for the request. A `tenantId` supplied in a URL, body,
  header, or query parameter is not authoritative.
- The Gateway routes to the service that owns the requested capability. That
  service independently validates the trusted identity context and enforces
  tenant and resource authorization before accessing its data.
- Service-to-service requests and events must carry tenant context in their
  documented, trusted form. Consumers validate that context and authorize
  access to their own resources; a message's tenant value alone is not proof
  of authorization.
- Service accounts and background operations use an explicitly established
  tenant context or a documented system-level scope. They must not infer a
  tenant from untrusted payload data or silently run without a scope.

## Logical model and ownership

```text
Tenant
  ├── Auth-owned memberships, roles, permissions, and role assignments
  └── Tenant-scoped records in service-owned schemas
        ├── customers
        ├── bookings
        ├── scheduling
        ├── jobs
        ├── payments
        └── notifications
```

Tenant is a logical scope shared by services, not a reason to create a shared
mutable data model. Auth owns identity and membership data. Each domain service
owns its records, tenant-scoped queries, and resource authorization. Services
do not read or write another service's tables. References to records owned by
another service are opaque IDs resolved through documented APIs or events,
not cross-schema joins.

Some data may be global by design, such as product-wide catalogs or
provider-defined metadata. Such data is not tenant-owned only when its
ownership and intended visibility are explicitly documented. Do not treat a
missing `tenant_id` as evidence that a record is safe to expose globally.

## Persistence and query invariants

- Every tenant-owned record is associated with its tenant using `tenant_id`.
  A table may omit this field only when its owner has documented why the data
  is global or derives an unambiguous tenant scope through an enforced
  ownership relationship.
- Every read, update, and delete is constrained by the trusted tenant context
  as well as the resource identifier. A resource identifier is not a
  substitute for tenant authorization.
- Inserts obtain `tenant_id` from trusted backend context, not from an
  unchecked client-supplied field. If a documented API accepts a tenant
  identifier, the backend verifies that it matches the caller's authorized
  context before persistence.
- Tenant scope is included in logical uniqueness and relationship rules
  wherever records are tenant-local. The owning service defines concrete
  unique constraints and foreign-key behavior so that duplicate keys or
  references cannot accidentally cross tenant boundaries.
- Database transactions preserve the same tenant context for every operation
  in the transaction. Connection-pool reuse must not leak one request's
  tenant context into another request.
- Apply tenant filtering to ORM relationships, pagination, aggregates,
  reporting, exports, and bulk operations, not only single-record lookups.
- If PostgreSQL row-level security (RLS) is enabled, treat it as defense in
  depth alongside application authorization and tenant-scoped queries. The
  owning service must define and test its policies, trusted tenant-context
  setup, and behavior for missing context. The current docs do not establish
  RLS as a universal implementation requirement.

Example logical query pattern (not prescribed SQL or an approved schema):

```sql
SELECT *
FROM service_owned_records
WHERE tenant_id = :trusted_tenant_id
  AND id = :resource_id;
```

The equivalent tenant predicate is required for mutations as well. If a
resource is not found within the caller's authorized tenant scope, the API
must follow the owning service's documented safe not-found behavior and must
not disclose another tenant's resource existence.

## API, events, and asynchronous work

- Public request DTOs do not expose tenant context as a client-controlled
  authorization mechanism. The Gateway establishes context from the
  validated identity; services validate it again.
- API and event contracts use `tenantId`; PostgreSQL uses `tenant_id`. These
  names identify the same logical scope but do not make caller-provided data
  trusted.
- An owning service authorizes a resource before returning or changing it.
  Gateway aggregation, a valid JWT, a visible module, or a tenant assignment
  does not replace that check.
- A service publishes domain events only after durable persistence. Events
  include tenant context where needed for the documented consumer workflow;
  consumers validate the event schema and apply tenant-scoped authorization
  before acting.
- Queue consumers, scheduled work, retries, and dead-letter replay preserve
  the original authorized tenant scope. Administrative or system-wide
  operations require an explicit, auditable scope and cannot be modeled as an
  ordinary tenant request with a missing tenant value.
- Cache keys for tenant-owned data include the tenant scope. Invalidation,
  deduplication, and idempotency scopes must not cause results or effects to
  be shared across tenants.

## Authentication, authorization, and operations

The Gateway validates the JWT, while the owning backend service enforces
authorization for its own data. Auth owns memberships, roles, and permissions;
domain services retain responsibility for tenant and resource-level checks.
Use least privilege for service identities and database access, and avoid
shared credentials or direct cross-service table access.

Audit records identify the actor, tenant, action, target resource, outcome,
and `correlationId` where applicable. Logs, metrics, traces, and errors must
not disclose secrets, tokens, or cross-tenant resource details. Tenant context
may be used for authorized troubleshooting and audit, subject to the system's
data-handling requirements.

## Isolation verification

Each service should test isolation at the boundaries where it reads or
mutates tenant-owned data. Tests should include:

- A caller in tenant A cannot read, update, delete, or infer the existence of
  tenant B's records by changing an identifier or submitting tenant B's ID.
- A multi-tenant user can access only the tenant selected and authorized for
  the current operation.
- Inserts, nested relationships, list endpoints, counts, exports, and bulk
  mutations remain scoped to the active tenant.
- Background jobs, event consumers, retries, and pooled database connections
  preserve tenant context and do not reuse it across tenants.
- Missing, malformed, revoked, or mismatched tenant context fails explicitly
  according to the owning API contract; it does not broaden access or fall
  back to a default tenant.
- Database constraints and any configured RLS policies reject or restrict
  cross-tenant access as intended.

## Decisions before physical implementation

The current `/docs` architecture establishes tenant ownership and the
`tenant_id` convention, but does not specify all implementation details. Each
owning service must document:

- Which of its records are tenant-scoped versus intentionally global, and
  how tenant scope is derived for related records.
- Concrete keys, indexes, uniqueness constraints, and relationship rules
  that preserve tenant boundaries.
- The trusted tenant-context propagation mechanism between Gateway,
  services, database operations, and asynchronous consumers.
- Whether and how PostgreSQL RLS is used, including policy ownership and
  behavior for absent or invalid context.
- Tenant-local cache, search, export, retention, backup, and audit behavior.
- The service's safe not-found and authorization error behavior without
  revealing another tenant's resource existence.
- Any explicitly supported cross-tenant administrative workflow, its
  authorization, audit requirements, and data-access boundaries.

Until those contracts are defined, do not infer tenant scope from user input,
assume global access for records without `tenant_id`, or introduce shared
tables and cross-schema access as an isolation shortcut.
