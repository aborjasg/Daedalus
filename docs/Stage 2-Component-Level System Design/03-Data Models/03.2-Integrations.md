# Data Model: Integrations

## Purpose and status

An integration connects a Daedalus capability to an external provider or
consumer. Its adapter translates provider protocols and payloads; the service
that owns the capability continues to own its business workflow and records.
For example, Payments owns payment-provider interactions and Notifications
owns message delivery.

The current architecture does not define a standalone Integration Service,
shared `integrations` PostgreSQL schema, or `/integrations/*` Gateway route.
The logical model below describes provider-connection metadata held by the
owning service. It does not establish a shared physical schema, table names,
or generic integration API.

## Logical entities

| Entity | Purpose | Owner |
|---|---|---|
| Provider connection | Represents a service's connection to an external provider for a tenant, including provider identity, safe status, and approved non-secret metadata. | Service that owns the integrated capability |
| Secret reference | Identifies a credential value stored in Azure Key Vault; PostgreSQL stores the reference, not the value. | Owning service stores the reference; Key Vault stores and protects the secret |
| Connection audit record | Records safe administrative changes and outcomes, with actor, tenant, target, action, and `correlationId`. | Responsible service and its established audit mechanism |
| Provider catalog entry (optional) | Describes provider options for discovery or setup if the product requires a shared catalog. | Not assigned by current service boundaries; must be explicitly owned before implementation |

These are logical concepts, not approved table names. Do not create a shared
`integration_secrets` table or a central catalog solely because older Shell
notes mention those names.

## Relationships

```text
Tenant
  └── Owning service's provider connection
        ├── provider metadata and connection status
        ├── Key Vault secret reference ──> secret value in Azure Key Vault
        └── safe audit history

Module (optional association by opaque identifier)
  └── Provider connection, only when the owning service contract requires it
```

The connection belongs to the service that uses it. Other services and the
Control Panel Shell do not join to or directly access its records. If a module
association is needed, it is a reference, not permission to access module
tables or transfer connection ownership. Module availability and Auth
permissions remain separate concerns.

## Connection data and invariants

The owning service contract defines concrete fields and types. The documented
model requires or permits these logical values:

- A service-owned identifier for the connection.
- Trusted tenant scope for tenant-specific connections; persisted as
  `tenant_id` where applicable.
- Provider identity and approved non-secret provider metadata.
- A `key_vault_secret_reference` for any stored provider credential.
- Connection status and rotation timestamps, as supported by the provider
  lifecycle.
- Standard service-owned creation/update metadata and optimistic-concurrency
  fields where the owning schema uses them.
- Audit metadata that identifies actor, action, resource, and correlation ID
  without storing secret values.

The database model does not specify exact column names beyond the
`key_vault_secret_reference` concept, provider metadata, status, and rotation
timestamps. Identifier format, status enumeration, uniqueness constraints,
metadata schema, retention, and concurrency policy must be defined by the
owning service.

## Secret storage and lifecycle

- Store credential and secret values only in Azure Key Vault. Never persist
  them in PostgreSQL, browser state, API responses, events, logs, or source
  control.
- Store only a Key Vault reference and approved non-sensitive provider
  metadata in the owning service's schema.
- The owning backend service uses managed identity and least-privilege access
  to resolve the secrets needed for its provider calls. The Shell never reads
  Key Vault.
- During setup, an authorized tenant administrator submits credentials
  through the API Gateway to the owning service. The service writes the values
  to Key Vault and returns only safe connection status and a reference-safe
  identifier.
- During rotation, update the Key Vault value and relevant service metadata
  without exposing the value. During disconnect, revoke or delete the
  credential according to provider policy and update or remove the reference
  and status as the owning contract specifies.
- Record safe outcomes for setup, rotation, and disconnect. Exact lifecycle
  states, retention, and recovery behavior are provider-specific and remain
  to be documented.

The database reference is not the credential, and possession of a reference
does not itself authorize access to the secret. Key Vault access policies and
identities enforce that boundary.

## Ownership and tenancy rules

- Each domain service owns the provider connection data and integration
  behavior required for its own capability. No service reads or writes
  another service's tables.
- Provider credentials are scoped to the intended tenant and owning service;
  do not share them across tenants or services unless a separately reviewed
  contract requires it.
- Derive tenant context from trusted identity context established by the
  Gateway. Never trust an arbitrary client-supplied tenant identifier.
- Auth owns users, tenant memberships, roles, and permissions. The Gateway
  validates JWTs, and the owning service independently authorizes connection
  operations and access to its resources.
- A visible setup page, role claim, module assignment, or valid JWT alone is
  not authorization to create, read, rotate, or disconnect a provider
  connection.
- Tenant-scoped records use `tenant_id` in PostgreSQL; API and event
  contracts use `tenantId`. Cross-service references are opaque identifiers,
  not cross-schema joins.

## API and operational boundaries

The Control Panel Shell submits setup requests through the API Gateway to the
service that owns the integration. The current route documentation does not
define a generic integration route or endpoint-specific request schema.
Each owning service must document its own routes, DTOs, error codes, status
behavior, authorization, and idempotency rules. Responses may include safe
status and a reference-safe identifier, never secret material.

The owning service is also responsible for provider timeouts, bounded retries,
idempotency where supported, and reconciliation of uncertain outcomes.
Provider callbacks, if supported, enter through the Gateway and must be
authenticated and validated according to the owning provider/API contract.
When a service publishes domain events, it does so after durable persistence;
events must not contain secret values or sensitive credentials.

Use `correlationId` to trace setup and runtime provider operations. Logs,
metrics, traces, and audit records must redact tokens, secrets, and sensitive
provider payloads. The Gateway translates downstream failures into the
canonical API error envelope without leaking provider internals.

## Decisions before physical schema

Before implementing or centralizing integration data, document:

- The owning service for every provider connection and its metadata.
- Whether a shared provider catalog is needed and, if so, its owner and API.
- The owning schema, concrete fields, uniqueness, tenant-scoping,
  concurrency, status lifecycle, and retention rules.
- Key Vault naming/reference policy, access identity, rotation and revocation
  behavior, and failure recovery.
- Gateway routes, request/response DTOs, authorization permissions, error
  behavior, and idempotency for setup and lifecycle operations.
- Provider callback authentication, event contracts, retries, reconciliation,
  and audit requirements where applicable.

Until those contracts exist, keep connection state with the capability's
owning service; do not infer shared tables or a standalone Integration Service
from this logical model.
